# Changelog

All notable changes to Spotifly will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added
- **A free account browses, and is told why this Mac does not play.** The accesspoint names the account's product after login in a `ProductInfo` packet (0x50), which reached `Accesspoint.handlePacket`'s `default:` and was dropped. It is now read: `type` is `premium` or `free`, among 101 flat XML elements (captured 2026-09-29, and kept, trimmed, as the test fixture). As under librespot, only `premium` plays here. For any other type, a play aimed at this Mac goes to the active device if there is one. With nothing active, such a play says "Playing on this Mac needs Spotify Premium." in the bar, where every play used to fail with a raw error, and the first one also raises a notice with Logout. The library, search and playlists are unchanged. The Mac is also no longer offered as a speaker, so a phone cannot transfer playback to it: it registers as the web player does when it cannot play, hidden and not a player, and still gets the device list. A login the accesspoint refuses with `premiumAccountRequired` is taken the same way, and its `AuthFailure` packet is now read instead of reported as "Server rejected authentication". Debug builds run a Premium account as free with `SPOTIFLY_DEBUG_ACCOUNT_TYPE=free`. Nobody here has a free account, so what one sees at login is still inferred. Plan: `plans/done/free-account-gets-no-explanation.md`.
- **Tracks Spotify will not play are greyed out, and stepped over.** Playlists, Liked Songs, albums and search results carry `playability` on every track, for example `{ "playable": false, "reason": "COUNTRY_RESTRICTED" }` (measured 2026-09-29), and it is now read into `Track.playability`. Such a row is dimmed in every list and the queue. Its tooltip says "Not available in your country: “…”", or "Not available on Spotify: “…”" where Spotify gives no country reason. A double-click on it says the same in the bar instead of trying to play, and so does starting radio from it, from a search card or a row; the menu's Play Next and Start Radio are disabled. Playback knows them too: the store keeps their uris, the logged-in view passes each change to the client, and the client also remembers any track that failed to load as unavailable. Next, Previous, auto-advance and the fetch-ahead step over them without loading them, so a playlist with withheld tracks plays through gaplessly and without a "Skipped" message for each. Play on an album or playlist, and the rewind at the end of a context, start at the first track that plays. The context resolver's answer carries no playability, so a context the app has never listed is still found out by loading, as since #57. Plan: `plans/done/unplayable-tracks-look-playable.md`.
- **Spatial Audio for Spotify's stereo.** `AVSampleBufferAudioRenderer` spatializes only multichannel content unless `allowedAudioSpatializationFormats` says otherwise, and every Spotify stream is stereo, so AirPods and similar headphones never offered it. The renderer now allows mono, stereo and multichannel; whether it is used, fixed or head-tracked, is the listener's choice in Control Center.
- **Spotify Connect handover in both directions.** Picking this Mac on a phone, or pulling playback here from Speakers, now takes it over: the `transfer` command's `TransferState` is read (context, track, position, options, queue — a track sent only by gid gets its uri back), the same context is resolved, and playback starts on the same track at the position it has reached since the sender's timestamp, paused if it was paused. Handing playback away works too: this device stops when another one takes over (librespot's `handle_cluster_update`), and its reported player state now carries what a receiving device needs to continue rather than restart — the context uri and url, the track's index and provider, the next and previous tracks, and the playback rate. While another device plays, the now-playing bar and the queue follow it again, as they did when main's Rust bridge pushed every cluster `player_state` to Swift; the port had dropped that, so the bar froze the moment playback moved. Verified live with two instances passing an album back and forth: the position carried over to the millisecond both ways (17502 ms after 17.5 s; 39436 ms after a further 21.9 s), a paused handover arrived paused, and a resume pressed on the device that had let go reached the new one as a Connect command.
- **The next track is fetched before the current one ends** — once it has played ten seconds, or thirty before its end at the latest — so Next and auto-advance start from memory: 61 ms from the press to an open decoder in a live run, where it was 540. The loaded track is kept for repeat-one and for previous, instead of being downloaded again, and the audio key and CDN url are requested side by side.
- **Add to Queue reaches the device that is playing.** While another device played, it appended to this Mac's own queue, which nothing was playing from, so the mirrored queue on screen never changed. It now takes the same local-or-remote route as pause and next and sends `add_to_queue` to the active device — the web player's own request, captured from its network tab and kept as the test's expectation. An album or playlist goes as its tracks, one command each. Verified with two instances: twelve commands sent, twelve received, and the sender's mirrored queue growing in step.
- **A theme switch in Settings**, under a new General tab: Light, Dark, or System. The choice is persisted as `appearanceMode` in defaults and applied live, no relaunch needed. Two mechanisms carry it, because neither alone covers everything: `.preferredColorScheme` on both scenes restyles the SwiftUI windows (setting `NSApp.appearance` alone demonstrably does not reach them), and `NSApp.appearance` covers what `preferredColorScheme` cannot, such as menus and alerts.
- Tests for the Swift playback stack, which arrived with none. The first were the playback queue's ordering (nine cases, including the shuffle crash below, which took the test process down with it before the fix) and the Shannon cipher's known-answer vectors from the twonky4/shannon reference — recovered from a self-test method nothing called.
- Environment hooks for testing without anyone at the keyboard, all inert unless set; `DEVELOPMENT.md` lists them:
  - `SPOTIFLY_DEBUG_AUTOPLAY=1` starts a fixed album shortly after launch, and `SPOTIFLY_DEBUG_DEVICE_ID` overrides the stored Connect device id.
  - With autoplay, `SPOTIFLY_DEBUG_PAUSE_AFTER=<seconds>` pauses and resumes 6 s later, and `SPOTIFLY_DEBUG_NEXT_AFTER=<seconds>` skips twice, that far apart.
  - `SPOTIFLY_DEBUG_TRANSFER_HERE_AFTER=<seconds>` pulls playback to this device, as picking it in Speakers does. With a second instance under another `SPOTIFLY_DEBUG_DEVICE_ID`, a handover runs both ways on one Mac.
  - `SPOTIFLY_DEBUG_TRANSFER_TO=<device name>` with `SPOTIFLY_DEBUG_TRANSFER_TO_AFTER=<seconds>` hands playback to that device through the Speakers path.
  - `SPOTIFLY_DEBUG_QUEUE_AFTER=<seconds>` queues a track and then an album through the context-menu path, locally or as Connect commands depending on which instance plays.
  - `SPOTIFLY_DEBUG_DROP_AP_AFTER=<seconds>` drops the accesspoint socket that long after login, the way Spotify resets it now and then, so the reconnect can be tested on demand.

### Changed
- **Artwork is drawn by one view.** The cards' `CardArtwork` became `Artwork`, which takes a size, a shape, a placeholder glyph, an optional shadow and whether to spin while loading. The album, artist and playlist headers, an artist's discography, the track rows and the library lists used to write out the same switch themselves, and now use it too. The one visible change is the placeholder: a secondary grey glyph on a grey fill everywhere, where the album and playlist headers, a track row's failed artwork and the now-playing bar drew the glyph in the primary colour, and the artist header drew a large person glyph with no fill. Plan: `plans/done/artwork-drawn-nine-ways.md`.
- **One way from a context's uri to its page.** `Route(contextUri:)` maps an album, artist or playlist uri to its page and Liked Songs to Favorites; the queue header's link and the `SPOTIFLY_DEBUG_OPEN` hook both use it, so the hook no longer opens Liked Songs as a playlist page. Plan: `plans/done/context-uris-open-one-way.md`.
- **Keyboard shortcuts are registered once, as menu commands.** Space, ⌘←, ⌘→, ⌘L, ⌘1–⌘4 and ⌘F existed twice, as hidden zero-size buttons and as menu commands with the same actions. The hidden buttons are gone. A probe in the test host settled the one thing that could have changed: the menu's plain-Space Play/Pause does not take keystrokes from a text field, which still types its space. The menu's ⌘1–⌘4 and Refresh now read the navigation as a scene value, so they work whatever has focus, as the hidden buttons did. Plan: `plans/done/keyboard-shortcuts-registered-twice.md`.
- **A withheld next track is found out ahead.** In a context the app has not listed, such as one started on a phone or a radio, a track Spotify withholds was found out only at the change of track, by loading it, and the one after it then loaded cold. The fetch-ahead, which starts ten seconds into a track, learns it much earlier and now says so: the pipeline reports `withheldAhead`, the client marks the track as a failed load would and names the one after it, and the change of track steps over the withheld one to a track already fetched. Tracks found withheld this way, or by a failed load, are greyed in the app too, since no list had said so. Plan: `plans/done/unplayable-tracks-found-by-loading.md`; what each attempt still cost was `plans/done/unplayable-track-attempts-cost-and-show.md`, and what is left of it `plans/open/withheld-tracks-left-to-find-out.md`.
- **A track load asks for its metadata once.** It asked `/metadata/4` first, which answers a stub without files these days, and extended-metadata only after that had answered: two round trips before the audio key and the CDN url were asked for, on every double-click, early Next, handover and skip past an unavailable track. Measured from the web player's session, the `Track` extended-metadata wraps carries the name and the duration as well, so it is the only request now. A track that does not exist still reads as not found: extended-metadata answers it HTTP 200 with a 404 in the entity's header and no `Track`, measured the same day. Plan: `plans/done/track-load-waits-on-two-metadata-requests.md`.
- **The queue is published with the track it moved to.** A skip, Previous, a jump from the queue or auto-advance published the new track at once, but the queue only after the track's metadata, key and CDN url had arrived, so for the whole load the store held the new track in the old lists and re-split them around it (`Queue.reconciled`), a workaround from the Rust bridge, whose early `SetQueue` lagged. The two now go out in one snapshot, and the re-split is gone. The fetch-ahead is still told the next track after the load, since telling it before cancelled a fetched-ahead copy of the track being loaded. Three races the re-split hid are closed with it: a Next pressed as a track ended could be followed by a second advance past the track it started, or under repeat-one by the old track again; and a pipeline state read before a skip could overwrite the skip's track in the bar. Plan: `plans/done/queue-rows-have-no-identity.md`.
- **Liked Songs is read as the playlist Spotify's own clients now use.** The web player no longer calls `fetchLibraryTracks`: behind two flags that default on, `enableLikedSongsListPlatform` and `enableLikedSongsAsPlaylist`, it pages `/collection/tracks` with `fetchPlaylistContents` on `spotify:playlist:37i9dQZF1F5p3rmiWPIYgZ` and plays that uri as the context. The uri is a constant in the bundle, the same for every account, and the service answers with the caller's own songs. The app now does the same (`LikedSongs` in `PathfinderLibrary.swift`): `TrackService.loadFavorites` pages that playlist with `PartnerAPI.likedSongs(offset:)`, and a double-click in Favorites plays it. Saves and removals stay on `addToLibrary`/`removeFromLibrary`. Checked against all 609 saved tracks of a real library before switching: both sources return the same tracks under the same ids, newest first, with the same `addedAt`, and the `Track` entities built from each match field for field, so nothing in the store changes identity. Gone with it: the `fetchLibraryTracks` operation, its three response types and variables, `Track(pathfinderLibraryTrack:uri:)`, and `PathfinderTrack.trackNumber`, which only the saved-tracks page ever filled in
- **Pathfinder hashes refreshed from the current web player.** Seven of the persisted-query hashes in `PathfinderOperations.swift` had been superseded by the live web client (`web-player.dea0f59e.js` and `xpui-routes-search.36497941.js`, harvested 2026-09-29): the four searches, `getAlbum`, `queryArtistOverview`, `fetchPlaylist`, and `home`, which had deliberately been held on the older `23e37f2e…` document until someone re-measured it. The rest — `queryArtistDiscographyAll`, `libraryV3`, `areEntitiesInLibrary`, `profileAttributes`, and both mutation hashes — still match the bundle. The old hashes were all still accepted, so this is ahead of breakage rather than a fix for it. Each changed operation was sent with the app's own variables under both hashes, from inside a signed-in web player tab, and the answers compared field by field against what the decoders read: every one came back identical, and the only differences in the bodies were additions (`onPlatformReputationTrait.verification.aiPersona` on search artists and on `queryArtistOverview`, `isAlbumPreRelease`/`preReleaseEndDateTime` on search albums and home shelf items, `ownerV2.data.socialHandle` on search playlists, `meV2` beside `albumUnion`, highlight colours on `homeChips`). So no decoder changed
- **Signing in ends on a proper page again.** The browser tab Spotify redirects to after login showed one unstyled line, "Spotifly is authorized. You can close this tab.", since the loopback callback server replaced librespot-oauth. It now shows the page the Rust login used to serve: a check mark on Spotify green, "Authentication Successful", and a pointer back to the Spotifly window. It is restored from `rust/src/oauth_success.html` as `Spotifly/Auth/OAuthSuccess.html`, and read from the app bundle. A redirect without a code, as after declining the consent, now gets a page of its own, `OAuthFailure.html`: "Authentication Failed" on grey. Before, that tab said Spotifly was authorized, as the Rust login's did. Both pages have an **Open Spotifly** button, a `de.rvdh.spotifly://open` link through the URL scheme the app still registers from its own-client-id days. Nothing handled that scheme, so SwiftUI answered each such URL with a second main window, with its own services and a second queue load. The main window now takes any external URL (`handlesExternalEvents(preferring: ["*"], allowing: ["*"])`), so the link brings the running app forward, or opens its window if it was closed, and never adds one. The browser's own request for the tab's icon now gets a bare 404. The one-shot listener would have taken it for the redirect had it arrived first, and it would have been served the page. Checked by hand with a Release build installed in `/Applications`: signing in ended on the success page, and **Open Spotifly** brought the app back. A declined consent was not tried.
- **The player reaches the UI through one observable model instead of ten Combine subjects.** The client keeps one `PlayerSnapshot` of what it tells the app, covering the connection, devices, active device, playback, queue with its context, and volume, and yields it on an `AsyncStream` that keeps only the newest (`Store/PlayerModel.swift`). `PlayerModel`, `@MainActor` and `@Observable`, applies each snapshot and writes only the parts that changed. Views read it from the environment, and `QueueService` and `PlaybackViewModel` follow it with `Observations`. No subscriber needs `.receive(on: DispatchQueue.main)` any more, where eleven did and two had trapped without it, and a stalled main thread finds the newest state instead of working through a backlog. `ConnectionService` is gone, and the store no longer holds the connection or the devices. Inside the engine, the pipeline's and the session's events each reach the client on one stream with one consumer loop, instead of a task per event that could be handled out of order. Remote commands still run concurrently, but start in the order they arrived. The cached position, active-device flag and connection flags are behind `Mutex` instead of `nonisolated(unsafe)` vars and an `NSLock`. Local skip, seek and radio report failures instead of dropping them with `try?`. Leftovers of the FFI went: the unused `becameActive`/`becameInactive` publishers, the connection state's `revision`, `Codable` keys, always-nil connection id and `spircReady` (the same value as `sessionConnected`), a second `ForceReconnectOutcome`, the queue published twice as `SetQueueNotification`, and the loading notification. Plan: `plans/done/player-interface-after-the-ffi.md`.
- **Playback and Spotify Connect run in Swift, and librespot and Rust are gone.** What librespot did for the app — the accesspoint session and its encrypted channel, audio keys, CDN downloads and decryption, and Spotify Connect over the dealer and connect-state — is ported to Swift in `Spotifly/SwiftLibrespot/`, and Ogg Vorbis is decoded by libvorbis and libogg, vendored as C in `Spotifly/Vendor/`. Building needs no Rust toolchain and no librespot checkout; librespot stays the reference for the protocol. Verified against a real account from the first run — the album context resolves, tracks decrypt (`OggS` head confirmed), decode in real time and advance — which needed:
  - RSA public-key DER long-form length encoding (2048-bit modulus overflowed the single-byte form — crash at handshake).
  - Accesspoint rotation with a bounded TCP connect; per-device AP throttling after aborted handshakes otherwise wedged startup silently.
  - spclient requests signed like the desktop client (`Client-Token`, `App-Platform`, `Origin`) and routed through `/context-resolve/v1/` (not v2), with audio files fetched from `/extended-metadata` `TRACK_V4` — `/metadata/4` returns a stub without file lists, and relinked tracks keep their files under `alternative`.
  - The dealer websocket session retained (a deallocated URLSession killed the socket), PutState gzipped + percent-encoded connection ids.
  - Spotify's container quirk: one leading non-vorbis page (flags `0x06`, typically 167 bytes) before the real BOS page — skipped by parsing segment tables rather than hardcoding.
- **Requires macOS 27**, for the audio output below. The deployment target is 27.0 — iOS and visionOS too, which the project also lists — and building needs Xcode 27; `README.md` and `DEVELOPMENT.md` say so.
- **The audio output is fed through macOS 27's renderer receiver.** `AVSampleBufferAudioRenderer.Receiver.enqueue(_:)` suspends until the renderer wants more audio, so decoding is now a task on the pipeline actor that awaits each 93 ms chunk. The wait paces it and holds it through a pause, and a flushed or cancelled enqueue returns at once. The ring buffer, the write throttle and its paused clock, the feed callback, the semaphores, the decode thread with its join thread, the pause condition and the `AudioSink` protocol are all gone: `AudioRenderer.swift` is 221 lines where it was 587, about 500 fewer across the audio path. Every call the old renderer made is deprecated in macOS 27. On the renderer alone (`docs/cpu-benchmark/renderer/run.sh`, three alternating runs each), against a version fed from its `requestMediaDataWhenReady` callback: 0.9–1.0 → 0.0 idle wakeups a second, 1.12–1.17% → 0.72–0.73% of a core, energy impact 1.1 → 0.7. In the app, Release, through the MacBook Air's speakers: playing, 1.0 idle wakeups a second and an energy impact of 2.3, where 1.2.7 measured 17.7 and 3.5; paused, 0.2 and 0.18% of a core. Checked live: a paused handover (the held renderer pre-rolls, so resuming is immediate), resume, seek, Next, volume from the web player, and a gapless change of track.
  - The pipeline's transitions — load, seek, pause, resume, stop, refill — run one at a time, through a small gate on the actor, and the position tick and a gapless continuation stand aside while one is under way. Two codex reviews found the windows that made this necessary once starting to decode awaited the renderer: a stop landing in that await was overridden, and the start went on to launch a decode, restart the position timer (four wakeups a second, for good) and report playing; pause and resume published their state after the await; the tick could end a track a stop had just torn down; a seek could apply its position to a track loaded while it waited; and at a gapless boundary a tick could adopt a continuation whose decode a seek or a teardown had just cancelled. A load takes the gate twice, around its download, so neither a pause nor a newer load waits on the network, and a stop now supersedes a load still downloading, which used to start playing when its file arrived. Checked live: a paused handover, resume, seek, a seek to 0, Next, pause, resume, a gapless change and a stop at the end of a context.
  - A change of output device does not silence playback. The old renderer was rebuilt, renderer and synchronizer both, on its auto-flush notification. The receiver reports a change of the renderer's own device as a suggested flush on the next enqueue. A change of the system's default output does not come back at all: switching speakers or AirPlay in Control Center makes the renderer drop what it had queued, the waiting enqueue never returns, and the clock runs on over silence. Measured with a probe, every time, on macOS 27.0. The renderer now reports itself stalled when an enqueue has waited half a second with less than a quarter of a second left queued; in normal playback it asks again at about 0.9 s. The pipeline's position tick checks for that and reloads from the playhead, as a seek there would, skipping the second or so that played as silence. A stall in the last second or so of a track, with gapless on, is noticed only after the clock has run into the next track, so a crossed boundary is adopted before the refill measures anything (from a codex review: the refill sought to the old track's end and stayed silent). Checked live, switching between the display's speakers and the MacBook's in both directions.
- A performance and simplification pass over the Swift stack, net about 1,600 lines smaller while gaining the handover and the prefetch above. **Connecting took five seconds of arithmetic**: the hand-written big integer behind the Diffie-Hellman exchange reduced one *bit* at a time, and the accesspoint login now completes about 230 ms after the session starts, where it took 5.3 s — replaced by Montgomery multiplication for the one prime the protocol uses, 199 lines instead of 426, with known answers from Python. Audio decryption made a quarter of a million CommonCrypto calls per track and is now one CTR cryptor. Five protobuf implementations — the client-token helper and hand-rolled tag-and-offset code in the handshake, the login, connect-state and spclient — became one shared codec, with every outgoing message pinned byte for byte first: `KeyExchange` went from 629 lines to 117, `Authentication` 275 to 85, `Connect` 1181 to 572, `SPClient` 760 to 424. The accesspoint no longer logs key material or hex-dumps every packet. A silent accesspoint is given up on after 5 s instead of 30, which live cost half a minute of startup once. Decoded audio is interleaved with one strided copy per channel instead of a scalar loop per sample, and the decoder has its first test, against a real Ogg Vorbis stream with different content per channel.
- A quality pass over the Swift stack once the review fixes had landed: about 550 lines removed with no behaviour change. `ConnectStateBuilder` was an entire file nothing referenced; `DealerMessage` carried hand-written mirrors of two protobuf messages that `Proto/Connect.swift` actually parses, and nothing constructed or read any of them; a `sessionClientChanged` publisher had neither a sender nor a subscriber, and `connectionIds` had a sender and no subscriber. Sixteen further members had no callers at all, including a self-test for the Shannon cipher — whose vectors were kept, as tests. The bitrate setting was mapped to a stream quality in three places and is mapped in one now, and `SessionState` hand-wrote the equality Swift synthesises. About fifty comments still described the deleted Rust bridge in the present tense and now describe what the code does; the ones that are genuinely history explaining a design choice were kept as history, and `docs/librespot-connections.md` now says which binary its `RUST_LOG` section is about.
- The documentation describes the app as it is: no librespot, no Rust. `DEVELOPMENT.md` is rewritten around the Swift stack (it still described a Rust OAuth library behind a "Connect with Spotify" button, from before either stack), with the debug environment variables and the two sign-in traps; `CONTRIBUTING.md` no longer asks for a librespot checkout beside the repo; `RELEASE.md` no longer requires `libspotifly_rust.a` before archiving; `AGENTS.md` says where playback lives. The librespot-era documents — the integration review, the connection architecture, the stability plan, the plans index and the librespot plans — now say what no longer applies, and the connection architecture maps librespot's parts onto the Swift files. The README credits librespot and the Xiph libraries.
- The connection section in Speakers is headed **Spotify Connection** (Spotify-Verbindung, Connexion à Spotify) instead of "Librespot Connection": there is no librespot left to be connected to. The string key moved from `speakers.librespot_connection` to `speakers.spotify_connection`.
- The accesspoint's acknowledgement of our pong, packet 0x4a, is named `pongAck` (librespot's and go-librespot's `PongAck`) and handled quietly, so the log no longer prints "Unhandled packet type: unknown" every two minutes. A packet still unknown is logged with its byte: the one left is 0x1f, once at login, which librespot cannot name either (`UnknownDataAllZeros`).
- Artwork placeholders swap their fixed `Color.gray.opacity(...)` fills for the adaptive `.quaternary`/`.tertiary` hierarchy, which reads correctly on both appearances instead of going muddy on dark.
- A simplification pass over the partner-API migration, removing about 820 lines without changing behaviour. The migration's leftovers were the bulk of it: `APITypes.swift` is gone entirely, since only two of its types still had a caller once entities stopped being built from Web API responses, and the survivors moved to the files that use them. The duplication that mattered was in the two partner clients, which held byte-identical copies of four stored closures, the same five signing headers, and the 401-invalidate-retry dance **three times** — with the rule about naming the token that was actually refused restated in three separate comment blocks, which is exactly how three copies drift apart. That is one `SpotifyCredentials` now, and the rule is written once. The Pathfinder wrappers had accumulated three private `Duration` structs and two `ArtistList` types structurally identical to the one already at the top level.
- A second simplification pass, this one over the whole codebase, removing about 1,480 further lines. The largest single item: `AlbumsListView`, `ArtistsListView` and `PlaylistsListView` were 815 lines that differ, once the entity noun is normalised away, in **two lines** between albums and playlists and four between albums and artists — everything else, including the ephemeral section, the back button, the divider rules and the pagination trigger, was byte-identical. They had already begun to drift, one having lost a comment the others carry and another writing the same shape two ways. They share `LibraryListView` now, with a style value that is literally the table of differences: two glyphs and an artwork shape. `FavoritesListView` deliberately stays separate — no coordinator, no selection, a different divider inset, and rows needing four more parameters. The same story in miniature for the four cards, whose artwork block was byte-identical and is now `CardArtwork`; the cards themselves are *not* unified, because only the artwork was actually shared. Twelve toolbar actions each spelled their localization key twice, once in the `Label` and once in the `.help`, with nothing keeping the two in step.
- Dead state that the partner-API migration stranded: `Queue.isLoading` and `Queue.errorMessage` had no writer left anywhere, so the queue's error banner could not appear under any circumstances; `SidebarView.onLogout` was never referenced; `NavigationCoordinator.setStore` had no caller. `NavigationDestination` also carried a hand-written `Hashable` conformance identical to the synthesized one, and `Route` a hand-written initializer justified by a premise — that the memberwise initializer cannot carry defaults — which is simply not true of optional `var`s.

### Fixed
- **A read that fails while the network stays up is asked for again, and so is artwork.** A server error or a dropped connection left the network up, so nothing counted as its return: a page or list showed its error until Try again was pressed, and artwork kept its placeholder until the view was rebuilt. Reads to Spotify's APIs are now asked for again in place, after 1 and then 3 seconds, for HTTP 5xx and for a connection that dropped or could not be made, including spclient's preflight. Each pathfinder operation says whether it is retried: the playlist and library writes are not, since a write that failed may have happened, and neither is the check behind each heart. A 404, a 429, a timeout, or a request made with no network at all fails at once as before. A failed artwork is asked for again after 5 s, 30 s and 3 min, and then left, so an image the CDN does not have is not asked for forever; offline it waits for the network's return. Plan: `plans/done/loads-that-fail-while-online.md`.
- **A skip onto a withheld track goes on past it.** Next, Previous and a jump in the queue stepped over a track Spotify withholds only once they knew of it; one they did not, from a context the app never listed and not fetched ahead, was loaded, failed, and stopped playback with "not available". Every load now goes on past it, in its direction, as auto-advance did and as librespot does: Previous back to the track before, Next, a jump, a play and a handover on to the track after, with "Skipped, not available" in the bar. A context with nothing that plays stops, named. Plan: `plans/done/skip-onto-a-withheld-track-stops-playback.md`.
- **Next works on an album's or playlist's last track.** The bar greyed Next whenever the queue listed nothing after the current track, which on a context's last track with repeat off is always so, for this Mac's playback and for another device's alike. But Next there goes back to the first track, paused, in Spotifly's player as in the web player's, so it is now enabled wherever a track is current. ## [1.2.7] - 2026-08-14

### Added
- `SpclientAPI`, the REST half, starting with `metadata/4` track metadata. Same two credentials as the GraphQL client but plain REST, which makes it the more stable half to depend on: no query hashes to rotate, and entities come back whole rather than field-selected. Two details are mimicked from the real client rather than guessed at — a CORS preflight goes before the GET, since the endpoint is served to the web client's origin, and `market=from_token` resolves the catalogue against the account rather than the caller's IP. It also brings `SpotifyGID`, which converts the base62 ids the app uses into the hex form spclient addresses entities by; the conversion refuses an id too large for sixteen bytes rather than wrapping, since a silently truncated id would address a different track. The protobuf endpoints on this host — extended-metadata, storage-resolve — are deliberately left out until the Swift playback track needs them
- `PartnerAPI`, the pathfinder GraphQL client, with the four search operations `SearchService` needs — tracks, albums, artists and playlists. Nothing calls it yet; search still goes through the Web API until the migration task moves it. The API takes some explaining: `api-partner` accepts **persisted queries only**, so no query document is ever sent. The request is an operation name, its variables, and a SHA-256 hash naming a query Spotify holds — which means the field selection lives on their servers and cannot be changed here, and only the variables are ours. The hashes are vendored from libspot, and they rot: a new web-client release eventually retires them, so a `PersistedQueryNotFound` is surfaced by name rather than as a generic error, and the header comment records how to harvest fresh ones from the live web client if copying from libspot ever stops being enough. Two shapes needed bridging: search results identify albums, artists and playlists by URI alone with no `id`, while `AppStore` keys entities by id, so the id is derived once in `SpotifyURI`; and an unreadable item is dropped rather than failing the whole page, since one odd entry should not empty a search
- The `Client-Token` handshake, which is the second thing both partner APIs require alongside the bearer — a token identifies the *application*, so it is fetched unauthenticated and is independent of the keymaster grant. `clienttoken.spotify.com` speaks protobuf, so this brings a minimal writer and reader with it rather than a code-generation toolchain: the request is four scalars inside three nested messages, and the response needs two fields out of it. Field numbers come from `spotify.clienttoken.http.v0`, and the macOS platform submessage is sent empty, exactly as libspot does. The device id is stable across launches and stored in defaults rather than the keychain — it identifies the installation, not the user, and a fresh one each launch would look like a new device every time. Tokens are cached until they expire, concurrent callers share one fetch, and `invalidate()` exists for the 401 case where a token is dead before its stated expiry
- `KeymasterSession`, which holds the keymaster tokens and keeps them valid. An actor, because the token is about to be read from several places at once — the accesspoint session, pathfinder and spclient — and a refresh has to happen once rather than once per caller. Concurrent callers arriving during a refresh join the one already running, since two refreshes would each spend the same rotating token and the loser would then persist a replacement Spotify had already invalidated. The tokens are stored as one keychain item rather than a key per field, unlike the Web API half: the four values are only meaningful together, and a single write cannot leave an access token paired with another grant's expiry. Two subtleties are pinned by tests rather than by comments — the second refresh must spend the token the first one returned, and a refresh that omits the username must not blank the one the accesspoint needs, since only the initial exchange carries it
- A Swift implementation of the keymaster grant — `KeymasterAuth` plus a one-shot loopback listener — which is the first step of `plans/done/single-grant-partner-api.md`. Nothing calls it yet; the Rust grant still runs the flow. It exists in Swift because Swift is where the *token* has to end up: the same token that logs into the accesspoint also authorizes pathfinder GraphQL and spclient REST, and Rust currently mints it, hands it to librespot and drops it. `ASWebAuthenticationSession` cannot serve this flow at all, since Spotify's desktop client id is registered with a plain-HTTP loopback redirect rather than a custom scheme, so the browser opens normally and an `NWListener` on a system-assigned loopback port catches the redirect — one request, one reply, then it closes. The wait is bounded, because the other end of it is a person and a closed browser tab produces no request at all. The `state` parameter is checked before the code is read: anything on the machine can reach a loopback listener, and the state is the only thing tying a redirect to the request that started it. Two facts here were measured against the live service rather than assumed — the exchange needs no DPoP proof and no client token, and Spotify **rotates the refresh token on every refresh**, so the response's token replaces the stored one. Keeping the original would make the *second* refresh fail, roughly an hour in, presenting as a spontaneous logout rather than as an auth bug
- An "Enable playback" step, which is what actually restores local playback. It runs the streaming grant and appears in three places: as a step between logging in and the app, as an "Enable this Mac" row in Speakers, and as an alert when a play request has nowhere to go. The three exist because the state they describe is not "playback is off" but "this Mac is not a playback device" — and without a grant this Mac never registers with Spotify Connect, so it is genuinely missing from its own Speakers list. That absence is the indicator; the row is the way back. The alert appears only when nothing anywhere can serve the request, never while a remote device is playing. The login step is skippable and the skip is not remembered, since the prompt is worth re-offering and Speakers carries the same button either way. Existing users land on it once after upgrading, because their session predates the grant
- `SpotifyAPI.startPlayback`, which starts content on a remote device over the Web API. The player extension had transport controls only — pause, resume, next, previous, seek, volume, shuffle — so with no local Connect device a phone could be paused but an album could not be started on it. `resumePlayback` hits the same `/me/player/play` endpoint but sends no body, which resumes whatever is already loaded rather than starting something. The device goes in the query string, where Spotify reads it, not the body; an empty `uris` list is omitted rather than sent, since Spotify rejects an empty one and callers should not have to check first. Request construction is split into `makeStartPlaybackRequest` so the body and query can be tested without a network round-trip
- A one-time streaming authorization, `spotifly_authorize_streaming()`, which is what fills the credentials cache. It runs librespot's own OAuth flow with librespot's client id against a loopback redirect, then connects once so librespot persists the AP credentials. Two client ids are now in play and they are not interchangeable in either direction: `clienttoken.spotify.com` returns 400 for a dashboard client id, so it cannot obtain the client token login5 requires, and a token minted with librespot's id returns 429 from every Web API endpoint — both measured against the live service. The loopback port is chosen at runtime by binding port 0 rather than hardcoded, since Spotify accepts any loopback port for a first-party id and a fixed one would collide. There is no in-flight cancellation: the flow's own listener bounds it, and the UI's Cancel declines before it starts. Because librespot persists from inside `Session::connect`, a logout landing mid-connect is caught *after* the write rather than before it — the run then removes the credentials it just created instead of leaving them behind for the account that logged out

### Changed
- **Spotifly no longer needs a Spotify Client ID.** Signing in is one button and one browser round-trip; the Client ID field, the developer-dashboard signup it required and the second "Enable playback" step that followed it are all gone. This was never a preference — the Web API refuses to answer without a registered app, and Spotify's own client id is refused by the Web API in turn, so browsing and playback each needed their own grant and the user had to supply half of it themselves. Nothing calls the Web API any more, so the app authorizes with the same client id the desktop client uses, once, for both. Existing users stay signed in, because the grant they already completed for playback *is* the grant: it is the credential every request has been carrying since the migration. Anyone who skipped that step signs in once more. Gone with it: `SpotifyConfig`, `SpotifyAuth`, `SpotifySession` and the Web API's keychain items — which are actively deleted rather than orphaned, since a live refresh token for an app Spotifly no longer speaks to is not ours to leave on someone's machine
- Being signed in is now one fact rather than two. The gate is the keymaster grant in the keychain, which is what every request needs; librespot's own credentials file is deliberately *not* consulted, because the two can disagree and only one of them decides whether the app works. That also settles what happens when half a grant succeeds: the token is adopted before librespot connects, so a failed connect leaves a usable grant, and the honest outcome is an app that browses but is not a playback device — which Speakers and the play alert already offer to fix, in the same words they use for a grant that has gone stale. The account-mismatch guard survives its original reason: it existed because two grants could disagree permanently, and with one grant that state cannot exist, but re-authorizing from inside the app into a *different* account is silent in a worse way — the library, the queue and the now-playing bar go on showing the previous account — so it is still refused. Signing in has nothing to compare against and is not affected
- **No call reaches `api.spotify.com` any more.** The last four were playlist management — create, rename, delete and follow — and they do not move to pathfinder, because pathfinder has nowhere to put them: the web client's bundle ships no `createPlaylist` and no `renamePlaylist` operation at all. A playlist's own existence belongs to the playlist service at `spclient.wg.spotify.com/playlist/v2`, the same service librespot already reads playlists from. Its messages are `playlist4_external` protobufs **sent as JSON** — proto3's JSON mapping, in both directions — so plain `Codable` covers them and the app's hand-rolled `Protobuf.swift` is not involved, which was worth measuring rather than assuming since reaching for it would have been the obvious move. The giveaway that the mapping is real: an `int64` added-at timestamp arrives quoted, `"1786645835061"`, because proto3 renders 64-bit integers as strings
- Creating a playlist is **two writes where `POST /me/playlists` was one** — the service makes the playlist and answers its uri, and nothing puts it in the library until the rootlist is told to hold it. Deleting a playlist and unfollowing someone else's are, conversely, **literally the same call**: a `REM` against the rootlist, which is what `DELETE /playlists/{id}/followers` had been saying all along. Two envelopes carry these: creating sends a bare `OpList`, while every change to an existing list wraps its ops in `ListChanges` with a source. Three details are load-bearing and each is pinned by a test to the body the web client actually sends — `itemsAsKey` is what makes a removal name *what* to drop rather than *where* it sits, so a library that reordered underneath us cannot delete the wrong playlist; `ListAttributesPartialState` is a partial, so a rename must omit `description` entirely or it overwrites the user's text with nothing; and the rootlist is addressed by **username**, which means library membership cannot be changed before the profile has loaded
- The startpage is Spotify's own now, fetched with one `home` request instead of assembled from three. It used to be three fixed rows — top artists, top albums, recently played — and none of the endpoints behind them has a counterpart on the client APIs. `home` answers with the page the real client draws: a greeting and a list of titled shelves, 31 of them in the test account, holding albums, playlists and artists together. So the app renders **whatever arrives** rather than a layout of its own: the shelf list differs between accounts and between refreshes (two requests three minutes apart returned different sections in a different order), and a section type this app has never seen still draws as a shelf of whatever it holds. The saving is not just three requests down to one — `/me/player/recently-played` named its items by uri only, so the recent strip then cost a further request per album, playlist and artist on it, where `home` returns every entity inline. Item kind is decided **per entry, not per section**, because one shelf genuinely mixes all three
- One variable decides whether there is a page at all, and GraphQL does not say so. Only `timeZone` and `homeEndUserIntegration` are declared required; a request carrying just those two is answered `{"data":{"home":{"__typename":"GenericError"}}}` — HTTP 200, no `errors` array, and a body that decodes perfectly well into a page with no sections. The missing one is `sp_t`, and its *value* is never read: a real device id, a junk string and the empty string all returned the same 31 sections, so only its presence is load-bearing. `sectionItemsLimit` is deliberately not sent — it is not the display cap it looks like, since 3 returned 22 sections where the default returned 31, dropping whole shelves rather than trimming them
- The user profile comes from `profileAttributes` instead of `/me`. Everything `UserProfile` holds is in it: `username` is the same string the Web API returned as `id`, so nothing stored under the old one needs migrating, and only the profile URL is absent — a fixed form (`open.spotify.com/user/<username>`) rather than a fact. One knock-on: the profile now needs the streaming grant, since it runs on the keymaster token, which is also true of everything else the app shows
- Playback control runs on Spotify's own Connect API. The seven `/me/player/*` transport endpoints collapse into one — `POST /connect-state/v1/player/command/from/{from}/to/{to}`, which names the action in its body — with volume the exception, keeping its own path and verb and wanting 0…65535 where the app uses a percentage. The device list, the playback state and the queue are no longer fetched at all: **they arrive**. librespot already holds the dealer websocket and already receives the Connect cluster on it, and the cluster listener was reading `active_device_id` and `player_state` from each update while throwing away `cluster.device` — so the app was asking `/me/player/devices` for a list that had already been delivered. Two facts decided the split, and both were measured rather than assumed: reading connect-state over HTTP is rejected without an `x-spotify-connection-id` that only a dealer socket can supply, which is why the reads live in Rust; and commands need no such id, answering `200 {"ack_id": …}` from a bare authorized POST, which is why they live in Swift beside the other spclient calls. A command aimed at a device that does not exist answers `404 DEVICE_NOT_FOUND`, which is how the request shape was confirmed separately from the target being there
- Finding out that nothing is playing anywhere no longer costs a request. The Web API answered 404 and the 404 was caught; connect-state addresses its target in the *url*, so with no active device there is no url to build — the same condition, one round trip earlier, on a path the user is waiting on. A play request is likewise no longer split into `context_uri` or `uris`. What connect-state is *less* forgiving about is what it will play: this endpoint plays **contexts**, not tracks, so a single track is sent as a context with a `skip_to` naming it, a context with an offset as a `skip_to` with an index, and a bare list of tracks — which has no context at all — as an inline context carrying its own `pages`
- The queue bootstrap reads the cluster instead of the Web API, and gains history doing it. `/me/player/queue` returned no previous tracks whatsoever, so the bootstrap had to pass `previous: nil` and leave the queue's history to be refilled by something else; the cluster carries it. Two things fall out of having one source rather than two: the **freshness barrier is gone**, since it existed only because an HTTP snapshot could be older than a Rust callback that landed while it was in flight, and a snapshot that *is* the last callback cannot be — and `QueueService` no longer takes a token. The guard that matters is unchanged and still tested: an answer meaning "I have nothing to tell you" is shaped exactly like one meaning "nothing is queued", and applying the second when handed the first is what emptied the queue on every wake from sleep
- The library — saved playlists, albums, followed artists and favorite tracks — runs on the client's own API. This is where the migration collapses rather than translates: three list endpoints (`/me/playlists`, `/me/albums`, `/me/following`) become one `libraryV3` query asked three times with a different `filters` value, and **six write endpoints become two mutations**, because `addToLibrary` and `removeFromLibrary` take uris of any kind — saving a track, saving an album and following an artist are now literally the same call with a different prefix. The three service methods stay separate anyway, since what happens around the call differs per kind and the views know nothing about uris. `/me/tracks` moves to `fetchLibraryTracks` and `/me/tracks/contains` to `areEntitiesInLibrary`. Four shapes were measured rather than assumed, and each would have been a silent failure: the saved-tracks page is the one track-bearing response where **the entity does not carry its own uri** — it sits on the wrapper as `_uri`, so reading `data.uri` would have returned nil for every row and emptied the favorites list; `areEntitiesInLibrary` answers **positionally**, with nothing in the response naming the uri it is about, so request order is the only thing tying answers to questions; `libraryV3` returns the same `PathfinderAlbum` as search but spells its date `{isoString}` where search sends `{year}`; and the mutations answer under names the operation does not predict — `addToLibrary` replies as `addLibraryItems`/`AddLibraryItemsResponse`, so the symmetry with `addToPlaylist` → `AddItemsToPlaylistPayload` gives the wrong answer and a client trusting it would call every successful save a rejection. Followed artists lose their special case: `/me/following` paged by cursor and was the only cursor-paginated list in the app, where `libraryV3` pages by offset like everything else, so `PaginationState.nextCursor` is gone
- Pagination now does its own arithmetic, because the client APIs report a `totalCount` where the Web API reported a `next` URL that was simply null on the last page. `PaginationState.advance(by:total:)` holds the two rules that are easy to get wrong: the offset advances by **how many entries arrived**, not by how many the app could use, and a page that yields nothing ends the list whatever the total claims. Both cases are real rather than defensive — relinking is many-to-one, so several saved track entries can resolve to one recording, and a page can hold entries the app drops. Advancing by the usable count would re-request the difference on every page; trusting the total alone would leave `hasMore` true forever and the list asking for another page it will never get
- Playlists are requested **flattened**, which restores the ones nested inside folders. `libraryV3` models the folder hierarchy the Web API never exposed, and the default view of it returns folders as entries and hides their contents — measured against an account with four folders: 10 playlists and 4 folders where `/me/playlists` had returned all 34. `flatten: true` with `includeFoldersWhenFlattening: false` reproduces the old flat list exactly. A folder is otherwise indistinguishable from a playlist by shape — it carries a `uri` and a `name` and decodes as one — so `PathfinderPlaylist.id` is now **kind-checked**: a folder's uri is `spotify:user:<user>:folder:<hash>`, and taking the last component of it yields a plausible id for something that is not a playlist. Proper folder *hierarchy* is a feature this does not attempt; this restores parity
- Playlists read and write through the client's own API. `fetchPlaylist` returns details and contents in one request, replacing `/playlists/{id}` and `/playlists/{id}/items`; the item writes — add, remove, reorder — move to pathfinder mutations. The operation *name* carries unusual weight here: `fetchPlaylist`, `fetchPlaylistContents` and `fetchPlaylistMetadata` all share one persisted-query hash and are selected by name alone, and asking for the wrong one returns a playlist with no tracks, or tracks with no names, rather than an error. Measured against a one-track playlist, they answer in 7144, 4396 and 3062 bytes respectively. The mutation shapes were established without writing to anything: sending each with no variables makes GraphQL reject it during validation and name the variables it wanted, and a deliberately invalid field returned the full SDL of `PlaylistItemPositionInput`, doc comments included. One behaviour is load-bearing and now covered by tests — **a rejected write comes back as HTTP 200** with a failure `__typename`, so a client checking only the status code would record a failed write as successful and leave its optimistic update standing
- Removing a track from a playlist now removes the one you picked, not every copy of it. The Web API identifies playlist entries by track URI, so removing a song from a playlist that contained it twice deleted both — and the client's own API identifies entries by a per-occurrence `uid` instead, which made fixing it the natural way to do the migration rather than extra work. `Playlist` now holds `[PlaylistItem]` (uid plus track id) where it held `[String]` of track ids; `trackIds` remains as a computed property, since most readers genuinely do not care which occurrence is which. Reordering is exact for the same reason: the drag handler names the item it moved and the item to place it before, so dragging one of two identical rows moves that row. One gap left deliberately: the context menu is shared by every list in the app and does not know which row it was opened from, so a removal from there still resolves to the *first* occurrence — better than removing all of them, and exact only once the uid is threaded through `TrackRow`
- The artist page runs on pathfinder: `queryArtistOverview` for who the artist is, `queryArtistDiscographyAll` for their releases, concurrently. Two operations rather than one because they divide that way — the overview knows the artist but returns only a *sample* of the discography (ten albums of fifteen for Daft Punk), while the discography query returns all thirty-seven and no profile at all, and the page offers "show all". Both hashes were harvested from the web player bundle and verified live; libspot has neither. Two shapes came off a real response rather than a guess, and both would have been wrong if assumed: releases nest as `items[].releases.items[]` — a release *group*, since one record can have several editions — except in `popularReleasesAlbums`, which puts the release fields directly on `items[]`; and the two operations disagree about dates, the overview sending `{day, month, year}` where the discography sends `{isoString, year}`. The sections also overlap, so releases are deduplicated: a repeat in a `ForEach` keyed by album id is undefined behaviour rather than a duplicate row. Discography entries carry a track count but no track list, so albums land unloaded and opening one fetches the rest, while the list can still say "13 tracks" for free. The recently-played strip moved to the overview operation too. Gone with it: `fetchArtistDetails`, `fetchArtistAlbums`, and the unreferenced Web API search path (`SpotifyAPI+Search.swift` and `SearchResultsCodable`), left behind when search moved to pathfinder
- Album details and their track list now come from pathfinder's `getAlbum`, in **one** request where the Web API needed two. spclient was measured as the alternative and rejected: its `metadata/4/album` returns `disc[].track[]` entries carrying a `gid` and nothing else, so rendering Discovery would have cost fifteen requests instead of one. The operation is the first hash that could not be vendored from libspot, which declares `OpGetAlbum` and then falls through to `panic("not implemented")` — it was harvested from the live web player bundle and verified against the service before use, and `libspot-probe/harvest-hashes.sh` now makes that repeatable rather than a one-off archaeology session. Two shapes were read off a real response rather than guessed: the track list is `tracksV2` (the sibling operation `getAlbumNameAndTracks` uses the same key for items holding only a `uri`, so reading the wrong one gives a track list with no names or durations), and album tracks are identified by `uri` alone with no `id` field. The album and its tracks are built together in one place, because they have to agree — an id in the album's `trackIds` that the store has no track for is a row the album view cannot render. The recently-played strip moved to the same call, so it stores the tracks it was already paying to fetch and opening one of those albums now needs no request at all. Paging is deliberately not implemented: `totalCount` makes a short read visible in the log rather than silently truncating an album, and whether this document honours `offset` was not measured — a paging loop built on an unverified offset can repeat a page forever. Gone with it: `fetchAlbumDetails`, `fetchAlbumTracks` and the `AlbumTracksCodable` envelope, which was the last type still projecting `linked_from`
- Track metadata comes from spclient now, so queue hydration and now-playing recovery no longer touch `api.spotify.com`. spclient is **id-faithful** — it returns the track you asked for, relinking nothing — which makes it exactly right for this path, whose job is to fill in ids the store already holds; the conversion still keys on the *requested* id rather than the returned one, so a day when those stop matching leaves a track unfilled instead of quietly adding a second entity for the same song. Two shapes needed bridging: `metadata/4` names a track's album and artists by gid where `AppStore` keys them by base62, so `SpotifyGID` gained the reverse conversion — refusing anything that is not 32 hex characters, since a nil album id merely leaves a track unlinked while a mangled one points at some other album; and cover art arrives as file ids rather than URLs, which are assembled against Spotify's image CDN. The real cost is request count: `/v1/tracks` took fifty ids at a time and `metadata/4` addresses one entity per request, so a batch is now one request per track, capped at eight in flight. The endpoint that batches this properly is `extended-metadata`, which is protobuf and stays out of scope until the Swift playback track needs it. One distinction is load-bearing and covered by tests: only a genuine 404 counts as "there is no such track", because that answer is remembered and the id never asked for again — anything else throws so the batch retries. Gone with the switch: `fetchTrack`, `fetchTracks`, the `/v1/tracks` envelope, and `TrackLookupViewModel`, which was the last caller of the first and was itself unreachable from anywhere in the app
- Search runs on the keymaster grant now, through pathfinder, and is the first thing in the app to stop calling `api.spotify.com`. It no longer takes a Web API token at all — that token is minted with the user's dashboard client id, which `api-partner` rejects — so the parameter is gone rather than passed and ignored. All four categories still come back, but as four concurrent operations rather than the single request the Web API served, since pathfinder has an operation per kind. Two shapes differ and are handled rather than papered over: search results identify albums, artists and playlists by URI with no `id`, so the id is derived from the URI; and pathfinder carries no `linked_from`, because it resolves the catalogue account-side and returns one entity whose id *is* the identity. That is correct for reading and for keying the store, but it leaves a question for the write paths — Spotify's relinking rules say a substitute id is the wrong one to save with — which is recorded where the conversions live and has to be settled before library and playlist writes move
- A streaming grant waiting on the browser can now be abandoned. Closing the browser tab without authorizing sends nothing at all, so the enable affordance kept spinning with no way back to it — the row was disabled while waiting, so it could not even be pressed again. It stays enabled now and cancels instead of starting a second grant, in Speakers and on the login step alike. This is possible only because Swift owns the flow: librespot's listener had neither a timeout nor cancellation, which is why the previous version had to leave Skip enabled and hope. Cancelling is reported as its own outcome rather than as a failure, so abandoning a grant no longer shows an error the user caused deliberately
- The streaming grant now runs in Swift, and Rust is handed the token it produced. `spotifly_authorize_streaming` no longer opens a browser, reserves a port or exchanges a code — it takes an access token and does the part only librespot can do: connect once so the AP credentials land in the cache. The move is not a preference for Swift but a consequence of what the token is for. The same token that logs into the accesspoint also authorizes pathfinder and spclient, so it has to exist in Swift regardless, and a token minted in Rust was dropped on the floor immediately after the connect. It is adopted into `KeymasterSession` *before* the connect rather than after, so a grant whose librespot half fails still leaves the app holding a usable token. Gone with the flow: `librespot-oauth` as a dependency, the `STREAMING_SCOPES` list (Swift requests them now), and `pick_free_loopback_port` with its test — Swift's listener binds port 0 itself, which also closes the small race where the reserved port could be taken between releasing it and the listener binding it. The account-mismatch guard, the credentials cache and the supersession checks are untouched. One knock-on: the clippy `not_unsafe_ptr_arg_deref` baseline on the FFI surface goes from 8 back to 9, since this entry point takes a pointer again
- Logging out now also removes the cached streaming credentials. They are a file in the app container rather than a keychain item, so clearing the keychain does not touch them — and left behind, they would let the next launch connect the account that just logged out, which is the same class of bug as the Spirc connection that used to survive a logout. Removed after the session teardown, so no live session can write them back on the way down
- Playing something with no local Connect device now starts it on the active remote device instead of failing. `play` and `playTracks` both opened with a `guard isInitialized else { errorMessage = "Player not initialized" }`, so when this Mac was not a playback device every play attempt was a dead end — even with a phone or a speaker active and perfectly able to serve it. The decision is now an explicit `playbackTarget`: local when the local player exists, the active device over the Web API when it does not, and only when there is neither does the user get asked to authorize streaming. That last case is the sole one that prompts — pressing play while a remote device is playing must not nag about local streaming. A remote start also resyncs afterwards, because with no Spirc session there are no playback or queue callbacks and the now-playing bar would otherwise keep showing whatever it showed before; the resync captures `liveStateRevision` before it awaits and skips the write if a logout moved it, since a superseded run must not write. `PlaybackViewModel` reaches `QueueService` through a reference injected at startup, mirroring how it already receives `AppStore`, rather than threading the service through six call sites in the views
- The librespot session connects from credentials cached on disk instead of from an access token. Spotify changed a server-side rule around 2026-08-11: login5 now rejects stored credentials that descend from a token minted with any client id other than its own desktop one, and Spotifly mints its token with the user's own dashboard client id. The AP still authenticates, so the failure lands one step later, at `Spirc::new` — `FaultyRequest(INVALID_CREDENTIALS)` — and takes local playback down completely while browsing continues unaffected. `Cache` is given a real credentials directory, which it never had, so `Session::connect` persists what the AP hands back and every later init connects from that with no token, no refresh and no round-trip beforehand. `create_session` resolves the credential itself — a freshly granted token when there is one, the cache otherwise — so callers do not each repeat the rule, and `spotifly_init_player` now accepts a null token meaning exactly that. Nothing yet writes to the cache; the grant that fills it comes next

### Fixed
- Logging out and signing in as a different account no longer hands the new one the old one's devices, queue and playback state. Four caches survived a logout: the three `CurrentValueSubject`s that replay the last update to a late subscriber — which is what makes a Speakers view opened at any moment show something — and Rust's own cluster snapshot. Replaying is right within a session and wrong across a logout: the new account's services subscribe and are handed the previous account's device names, with transfers aimed at device ids that are not theirs. The queue snapshot was the worse of the two, because the cold-start bootstrap's whole guard rests on an empty snapshot meaning "no cluster update has arrived yet" — a surviving one reads as "this is the queue", and the new account was handed the old one's. All four are emptied on the teardown rather than left to be overwritten, since if the new session never connects the old values are all the new subscriber ever sees
- A track added to a playlist whose refresh then failed no longer leaves the playlist stuck. Adding writes optimistically under a locally generated uid, because the mutation does not return the one Spotify assigned, and the reload behind it is what swaps in the real ones. If that reload failed the playlist stayed marked loaded with placeholders in it — so nothing fetched it again for the rest of the session, and removing or dragging one of those rows sent Spotify a `local:` uid it had never heard of. The contents are marked stale instead, which leaves the rows on screen and lets the next visit repair them. The rule lives on the reload rather than in the add, so a reorder whose refresh fails is covered by it too — its order is optimistic in the same way. Two things had to hold for that to be safe: a run that was *superseded* marks nothing stale, since whichever run replaced it owns the outcome and applies the same rule if it fails in turn; and a summary refresh from the library, search or the start page no longer erases the rows of a stale playlist, which it did because the preservation rule was keyed on the very flag being cleared
- A client token that dies before its stated expiry no longer wedges the app until it is relaunched. Both partner hosts want a client token beside the bearer, and it is cached for as long as Spotify says it is good for — a fortnight — so a token revoked early failed every request from both clients with nothing to notice it: `ClientTokenProvider.invalidate()` existed for exactly this and was called from nowhere. A 401 now drops the cached token and retries once, on `PartnerAPI` and `SpclientAPI` alike. Once, not in a loop: a 401 that survives a fresh client token is about the bearer or the account, and the bearer refreshes itself. The refusal names the token the request actually carried rather than dropping whatever is cached when it lands — requests run concurrently and share a token, so one dead token is refused several times over, and the later refusals would otherwise throw away the replacement the first one fetched, costing a handshake per refused request against an endpoint that can answer with a proof-of-work challenge this app cannot solve
- Creating, deleting, following and unfollowing a playlist no longer stay broken for the rest of the session when one startup request fails. All four address the rootlist by username, which comes from the profile — and the profile is fetched once at launch on a path that deliberately swallows its own failure, because an app that cannot say who you are is still an app that plays music. Nothing retried it, so a single hiccup there turned every library write into `accountUnknown` until the app was relaunched, for a request none of them had ever made themselves. They fetch it now when it is missing, through the request registry, so four writes arriving together still cost one request. A failure is still a failure — this is a retry on the next attempt, not a loop
- Cancelling a grant after the browser has already redirected no longer reports it as a connection failure. Only the browser wait answers cancellation with `CancellationError`; once the redirect lands the flow is inside `URLSession`, which reports a cancelled task as a `URLError` of its own, and that fell through to the failure branch — so pressing Cancel said "Could not connect to Spotify. Please try again." Cancelling is the user's own decision and is reported as nothing at all, on both halves now. The run that owns the in-flight grant is also named, so a run that has been abandoned cannot release the handle belonging to the one that replaced it — the window is a single hop, but an uncancellable grant with a second one able to start beside it is not a state worth leaving reachable
- Re-authorizing while signed in no longer risks logging you straight back out. Adopting a fresh grant left any refresh already on the wire running, and that refresh spends the token the new grant has just replaced — so it came back either with tokens that overwrote the new grant, or, more likely, refused as `invalid_grant` for a token Spotify had retired, which discarded the grant and returned the app to the login screen seconds after a successful authorization. Adopting now supersedes a running refresh the same way logging out does. Re-authorizing while signed in is a real path rather than a corner: Speakers and the play alert both offer it. The single-flight guard was tightened with it — a run that finishes after being superseded no longer empties the slot its replacement is holding, which would have let two refreshes spend the same rotating token
- A playlist longer than 300 tracks is fetched to the end instead of stopping at the first page. `fetchPlaylist` caps its answer at `limit` items and reports the real length as `content.totalCount`, and the migration read the first page and marked the playlist loaded — so a 500-track playlist showed 300 tracks and no error, on a screen that had paginated to the end when it ran on `/playlists/{id}/items`. The truncation was worse than a short list: an item the app never saw cannot be removed or reordered either, because both name a uid the app can only learn by fetching the row. The walk ends on a page that adds nothing rather than on reaching `totalCount`, since a playlist that loses items mid-walk would otherwise name a length no offset ever reaches
- Removing a track from the context menu now removes the row it was opened from. It was the last place in the app that still resolved a removal by *song* rather than by occurrence: a playlist holding the same track twice would lose whichever copy came first, whichever one you right-clicked. The uid is threaded through `TrackRow` to the menu, and it is **required rather than preferred** — the menu offers removal only when it can name the row, so there is no fallback left to land on the wrong one. Nothing is lost by that: the only screen that offers this is the playlist page, which has had the uid all along. The Web API path this descends from was worse again, removing *every* copy, because that API identified playlist entries by track uri and had nothing finer to offer
- A revoked grant is discarded instead of being retried forever. When Spotify answers a refresh with `invalid_grant` the token is permanently dead — revoked, or expired under the six-month policy — but nothing forgot it, so every later request spent the same dead token, and because the keychain outlives the process a relaunch resumed the same loop. The app looked signed in and failed at everything, and the only way out was to find the logout button and press it. It now clears both halves of the grant and returns to the login screen on its own. Two things are deliberate and each is covered by a test: **only `invalid_grant` counts**, read out of the response body rather than inferred from the 400 that carries it — Spotify sends the same status for a malformed request and an unknown client id, so keying on the status would sign a user out over a bug in this app, and everything else including 500s is assumed transient, because retrying a live grant costs a request while discarding one costs a sign-in. And **a revocation that a logout outlived clears nothing**, since the refresh spans a network call that a logout and a fresh sign-in can both land inside; the refusal belongs to the token that run spent, not to whatever holds the slot afterwards
- The volume slider greys out on a device that will not take volume, instead of failing after the drag. An iPhone declares `disable_volume` in its Connect capabilities — iOS does not let one app set system volume for another — and the app learned it only by sending the command and reading `400 DEVICE_DOES_NOT_SUPPORT_COMMAND` off the reply, by which point the user had already moved a slider that would not stay. The cluster carries the answer up front; Rust was dropping it. The popover also says which device is deciding, because a greyed control on its own does not explain itself. Absent capabilities still mean "nothing declared" rather than "volume refused", so only an explicit `true` disables anything. `volume_steps` is deliberately left alone — it describes granularity, not permission
- The Profile screen, and the logout button on it, no longer disappear when the account cannot be loaded. The router drew `UserProfileView` only when a profile was in the store, which was survivable while the profile came from `/me` on the dashboard grant — a broken *streaming* grant left the screen standing. Both now run on the same keymaster grant, so a revoked refresh token emptied the screen and took logout with it, and logout is precisely what clears a revoked grant: the app could not be recovered from inside itself, on any screen, across relaunches. The profile is optional here now and the button never waits on a request. Found the hard way — `libspot-probe` authorizes with the *same first-party client id* as the app, and Spotify keeps one live refresh token per client and account, so probing the API all afternoon revoked the app's grant
- Refreshing the startpage now shows that it is refreshing. ⌘R fetched, stored and redrew the page correctly, and looked like a dead key — because a reload of this page usually changes nothing visible: two `home` requests a second apart returned an *identical* first eleven shelves and differed only in the tail of one-item "Made for you" rows, far below the fold. `homeIsLoading` drove only the empty-state placeholder, which is hidden whenever there is content to hide it behind, so a refresh with shelves on screen had no visible effect at all. A spinner beside the greeting is what separates "asked, and got the same answer" from "nothing happened"
- A second refresh no longer stops the first one's spinner or its bookkeeping. **Cancelling a task does not stop it where it stands** — it unblocks the `await`, and the cancelled load then runs its own teardown, possibly after the replacement has already registered itself; clearing `loadTask` and `homeIsLoading` unconditionally there meant the loser cleaned up after the winner, turning the spinner off mid-load and sending the next caller to start a third request instead of joining the second. Reaching it takes only what a refresh that changes nothing invites: six ⌘R presses in four seconds, which is what the log actually recorded. The load now claims a generation and only the current one cleans up, as `DeviceService.transferPlayback` already did for transfers The Connect cluster is delivered over a dealer websocket that only carries **changes**, and librespot's own registration is answered in the HTTP response to its PUT rather than pushed — so a subscription alone never learns what is already there. Measured: registration completed at `:04.702` and the first push arrived at `:27.035`, twenty-three seconds later, and only because a phone connected; with nothing else on the account, a Connect-enabled stereo stayed invisible indefinitely. Rust now registers a **hidden member** — `can_be_player: false, hidden: true`, which is what any pure controller does — and reads the cluster out of the reply. Hidden because it is not a second playback device: librespot already registered the real one, and re-PUTing that id with a partial state would disturb its registration rather than ask a question. The fetched cluster and the pushed one go through one function, so what the app learns cannot depend on which told it
- Commands Spotify declines are no longer reported as errors. Thirteen of twenty-eight in one measured session came back as failures, every one a control pressed deliberately against a device or a state that would not take it: `403 skip_to_prev_restricted` with `no_prev_track`, and `400 DEVICE_DOES_NOT_SUPPORT_COMMAND` from an iPhone refusing a remote volume change, which is iOS policy rather than a Spotify one. Both surfaced as "Spotify rejected the request", which makes a working app look broken. `SpclientError` now carries the response body — a status code alone sends the next person to read code rather than the answer they were handed — and tells a refusal from a fault
- Previous does what its own button promises on a remote device. `hasPrevious` enables the control once playback is three seconds in even with no earlier track, because restarting is what pressing it means then, and the local player does exactly that; a remote device answers `no_prev_track` instead, so the button sat enabled doing nothing behind an error banner. The refusal is now answered with the seek it stood for
- Only one queue row is drawn as playing. `TrackRow` decided by uri, so a queue holding the same recording twice — an album with a reprise, a playlist a track was added to twice, or two catalogue entries relinking to one market id — lit up every copy while only one advanced. The queue already knew the answer and was already passing it: `currentIndex` sat there, used by the played-track check on the next line and ignored by this one. Position wins where a list knows both; an album page or a search result has no current position, so those are unchanged
- Reordering a playlist puts the track where you dropped it, instead of at the end. The drop handler mixed two frames: it captured the dragged row's index *before* the optimistic reorder, then used that index to read the *already reordered* array — so it usually named the wrong item to move, and the position it computed alongside was wrong in the same way. That had survived on the Web API because it took positions, which Spotify applied against the server's own order; the client's own API names items by uid and has no such slack. The move is now read out of the store *after* the optimistic reorder, where it is simply "put this item before whatever now follows it", and rows carry their `PlaylistItem` rather than just a track — so dragging one of two identical rows moves that row and not its twin
- The playlist page loaded again, and a rejected partner-API request now says why. `fetchPlaylist` was sent without `enableWatchFeedEntrypoint`, which its stored query declares — so Spotify answered 400 and the page showed "Spotify rejected the request (HTTP 400)". The variable is the fix; the reason it took a code read to find is the more useful part. A 400 from this API names the variable it wanted and its type, right in the body, and the client was discarding that and reporting only a status code. Rejection bodies are now logged and carried into the error, which is the same information the playlist mutations' schema was discovered from in the first place
- Playlists with no description no longer show the word "null" under their title. Spotify's playlist list answers with the literal string rather than an absent field, so the view's fallback never saw a nil to fall back from; it is normalised at the entity boundary where every reader gets the same answer
- The Now Playing bar no longer re-checks the playing track's favorite status over and over. It resolved the heart through `refreshFavoriteStatuses`, which skips the resolved cache by design, from a `.task(id: currentTrackId)` — and `.task(id:)` restarts whenever the view *appears*, not only when the id changes. One continuously playing track drew seven identical `/me/tracks/contains` requests in under two minutes, each returning the same answer. It now goes through the cache-respecting `ensureFavoriteStatuses`, which is what every other list in the app already uses, so the bar is consistent rather than uniquely chatty. What that gives up is noticing a favorite toggled on another device *while* the track plays; the right mechanism for that is Spotify's collection change feed, which already arrives over Mercury and is currently dropped unread. `refreshFavoriteStatuses` is removed rather than left dormant, since this was its only caller. The reason the bar re-appears as often as it does is not yet established — the track id itself was ruled out, as it is only cleared by `stop()` and by re-initialisation
- Opening Favorites no longer crashes when two saved tracks share one market recording. Relinking is **many-to-one**: several saved recordings can substitute to the same playable one, and since the market id is now the track's identity, a library page can legitimately name the same track twice. `markTracksAsFavorite` built its dictionary with `uniqueKeysWithValues`, which traps on the second — a hard crash on opening the section, for any account holding a pair like that. The list deduplicates across the whole of itself rather than per page, since the two names can also arrive in different pages, and one row per track is not cosmetic: `favoriteTracks` feeds a `ForEach` keyed by track id, where a repeat is undefined behaviour rather than a repeated row. A visible consequence is that the list can be shorter than the total Spotify reports, because that counts saved entries and this counts tracks
- Favoriting a relinked track from search works again, and the fix is a reversal: **the market id is now the track's identity everywhere**, where the app previously normalised every id back to the "original" through `linked_from`. A relinked track is one Spotify substitutes because the recording you asked for is not licensed in your market, and it has two ids — the app was holding one of them in search results and the other in the library, so the heart on a searched track stayed grey, and unfavoriting it missed. The old rule was not wrong when it was written: Spotify's relinking docs require the original id for Web API writes, and the Web API hands both ids over. What changed is that search now runs on pathfinder, which returns the market recording and carries **no `linked_from`** — there is no way to ask for the original back, and the substitute looks canonical from every angle. So the only id every path can agree on is the market one, and agreement is what the store actually needs: one entity per track, or the queue points at a key that misses and the track re-fetches forever behind a placeholder. `RelinkableTrackCodable`, `LinkedTrackCodable`, `logicalId`/`logicalUri` and the `linked_from(id,uri)` field projections are gone rather than left inert, since a dormant normaliser is exactly what would quietly reintroduce the second id. `market=from_token` stays on every request that takes it — that is what makes the Web API return the same recording pathfinder and playback use. Spotify's docs warn that a substitute id "will likely return an error or other unexpected result" when saving or removing; measured against the live service, it does not — saving and removing a relinked track by its market id both succeed, and Spotify's own collection service pushes the change back naming that same market id, with a timestamp matching the second the request was sent. So the warning is about third-party expectations rather than about what the service accepts, which is unsurprising once you notice Spotify's own client has no other id to send
- Logging out during the browser half of a streaming grant no longer leaves that account's credentials behind. The check itself is not new, but the ground moved under it: Rust used to hold the browser wait and snapshot the logout generation before it, so it could see a logout that landed during the wait. Swift runs the browser half now, so Rust's snapshot is taken *after* the logout and its own supersession check passes — the grant writes AP credentials and keymaster tokens for an account that is gone, and the caller's stale-run guard merely returned. That guard now undoes the run's own writes: it tears the session down and clears both halves of the grant, exactly as the wrong-account path already did
- A streaming grant authorized with a different Spotify account than the one signed in is now rejected instead of accepted. The second OAuth flow runs in the browser, with whatever account the browser is signed into — nothing tied it to the Web API session, so the app could browse, edit playlists and save tracks on one account while playing, queueing and controlling devices on another, with nothing on screen saying so. The grant now reports the account it authenticated as, and a mismatch clears the credentials it wrote and asks the user to sign the browser into the same account. Being unable to determine either side counts as agreement: refusing a grant because `/me` was briefly unreachable would be worse than the case being guarded against, which requires deliberately signing into a second account
- Four more defects in the streaming split, found by review before they reached anyone. A grant waits on a human in a browser, and `SESSION_GENERATION` advances on every rebuild rather than only on logout — so an ordinary play, retry or wake during that wait made the *successful* grant report itself superseded and delete the credentials it had just written; supersession now tracks a counter that only logout and app termination move. The device table was populated only by opening Speakers, and `activeDeviceId` derives from it, so the remote-playback path almost never triggered: a user who skipped the grant was told nothing could play while their phone was playing. Startup now keeps the device response it was already fetching for the premium check, and the play path refreshes once more before concluding that nothing can serve the request. Individual tracks were sent as `context_uri`, which Spotify rejects — `playTrack` and the queue both pass bare track URIs — so they now go in `uris`, with the offset dropped since it only means something inside a context. And Skip stays enabled while a grant waits, because the callback listener has no timeout and cannot be cancelled: closing the browser tab would otherwise strand a first-time user on that screen with no way in but relaunching
- Player initialization no longer hands librespot the Web API token, which is what kept playback broken and, worse, kept destroying the credentials that would have fixed it. `spotifly_init_player` had learned to accept a null token meaning "connect from the cached streaming credentials", but Swift still passed the dashboard-minted token, which `create_session` prefers over the cache — so login5 rejected it exactly as before. The compounding part: `Spirc::new` connects with `store_credentials = true`, so every one of those failed inits *wrote* its rejected credentials into the cache, overwriting the good ones a grant had just cached. The result was a loop where authorizing appeared to succeed and the next play attempt sent the user straight back to the browser. The token parameter is now gone from the whole initialization chain rather than passed as nil at the bottom, since a dead `accessToken` on an init function is what let this hide in the first place. A successful grant also builds the session immediately, so this Mac appears in Speakers instead of waiting for the next play
- `LoopbackCallbackServer.receiveRequest` no longer captures its local functions across a concurrency boundary unmarked. `finish` and `read` are both called from `NWConnection`'s receive handler, which is `@Sendable`, so they are declared `@Sendable` rather than left as ordinary local functions the closure happens to capture — four warnings for one defect, since the compiler reports both the declarations and the captures
- The `await` on the client-token invalidation is kept, and the warning calling it unnecessary is gone. That warning was the compiler's rather than the code's: a closure literal written in a *default-argument list* is not isolation-checked, so the hop onto `ClientTokenProvider` goes unnoticed there. Deleting the `await` would have silenced it, but the identical call one line outside a default argument is a hard error, and the SIL is the same either way — the executor hop is emitted whether the keyword is written or not. So the closure is hoisted into a `private static let` on `PartnerAPI` and `SpclientAPI`, where it is checked like any other code
- The last warning in the test target, which the six-warning sweep did not cover because it is not in the app. `PlaylistServiceTests`' fake transport declared `profile()` as `throws` and reached for `lock.withLock` with a `try`, but nothing inside it throws — the failure case it models is a 500 status code, not a thrown error. Both are gone, so the two halves of the fake now have the same shape

## [1.2.6] - 2026-08-12

### Changed
- `currentPositionMs` is derived instead of stored. Once `anchorPosition` owned the write, the field was assigned on every update to exactly `min(positionAnchorMs, trackDurationMs)` — a cache of a one-line derivation, whose only possible disagreement with its source was being stale. It is now computed from the anchor, so the view model holds one position instead of two that had to be kept in step, and the clamp both it and `interpolatedPositionMs` apply lives in a single `clampedToTrack` helper. One behaviour improves as a side effect: a duration arriving *after* a position now caps it, where the stored copy kept whatever value it was written with
- The once-a-second drift check is a `Task` instead of a thread and a notification. It ran on a manually managed `Thread` looping on `Thread.sleep`, which posted a `NotificationCenter` notification, observed on the main queue, which hopped to the main actor to call one method — about forty lines and a process-wide notification name to schedule a single timer. Its comment cited avoiding "Swift concurrency issues", which predates the project's settled `@MainActor` isolation; the view model is main-actor-isolated, so an awaiting `Task` sits on the right actor with no hop and no observer. Two loose ends went with it: the timer's `stop()` was never called and the observer was never removed, both harmless only because the view model is an immortal singleton, and the replacement is cancellable and holds `self` weakly
- Position anchoring goes through one method instead of eleven copies. `positionAnchorMs`, `positionAnchorTime` and `currentPositionMs` describe one fact between them — where playback is, and when it was there — but were assigned separately at every site that moved the playhead: initialization, next, previous, seek, resume, the disconnect freeze, the loading notification, the Mercury and Web API state handlers, the Rust anchor sync, and the drift correction. They had already come apart: two of those sites clamped `currentPositionMs` to the track length and eight did not, with nothing recording why. `anchorPosition(_:at:)` now owns the write and the clamp, so the frozen value agrees with the interpolated one, which clamps too; an unknown duration clamps nothing, which is what keeps a track change safe, since the URI `didSet` zeroes the duration before the new position arrives. The optional `at:` carries the one real variation — a Mercury or Web API snapshot that was true earlier and anchors its clock back by the elapsed time rather than restarting it
- Connection-state snapshots now carry a monotonic revision assigned by Rust, and Swift drops any that arrives after a newer one. Three Rust tasks publish independently — the event listener, the cluster listener, the reconnect loop — and the hop to the main actor gives no ordering guarantee between them, so a delayed callback could deliver an older snapshot last and leave subscribers acting on a readiness that was no longer true. The revision is assigned while the state is read, under its own lock, so it orders snapshots by what they actually saw; delivery stays outside that lock, because handing the payload to Swift re-enters the callback and must never happen while holding one. The synchronous `getConnectionState()` pull is published the same way, since Rust stamps it too — otherwise a callback already queued behind that call would overwrite what was just read, and merely suppressing that callback would leave the subject holding the older value. Two alternatives were rejected: re-reading the current state on arrival also fixes the ordering but erases readiness *edges*, and the recovery re-sync in `LoggedInLifecycleModifier` triggers on exactly that `false → true` transition; a serial dispatch queue is banned by the project's Swift guidelines and would not have ordered the snapshots anyway, since decoding happens before the hop
- Playback transfers are serialized instead of running concurrently. Each speaker row launches its own task, and `transferPlayback` optimistically marks its target active and undoes that when Rust rejects the transfer — sound only while nothing else is in flight, since overlapping attempts capture each other's optimistic values as the state to restore, and two rejected transfers could leave a device marked active that never became active. Attempts now chain onto the previous one, so the later tap still wins because it runs last. A rollback additionally only fires when no authoritative active-device update arrived from the cluster while the transfer was awaited — another client activating a device mid-transfer outranks restoring what was true before the tap, including when it names the very device that was asked for, which the store alone cannot tell apart from the optimistic update
- Logging out during a network outage now actually stops playback. `PlaybackViewModel.stop()` was gated on the session being connected, borrowed from the transport commands — those go through Spirc, which rejects them without a session, so acting on them locally would desync the UI. `spotifly_stop` is not one of them: it stops the Player directly, a local teardown that works while disconnected. The guard meant logout returned early during an outage, leaving buffered audio playing and the previous track still showing
- The queue refresh scheduled after a provisional `SetQueue` now retries instead of giving up silently. librespot emits a `SetQueue` carrying a context but no tracks while it is still filling one in; Swift keeps the existing queue and schedules a Web API refresh to recover the real one. That refresh was one-shot, and the freshness barrier discards the whole bootstrap response whenever a Rust callback lands mid-fetch — which is likely in exactly this window, since starting a context produces cluster updates. The safety net therefore failed silently and left "up next" stale until the next real `SetQueue`. `fetchInitialPlaybackState` now reports whether it applied anything, and the refresh re-attempts up to three times. The queue contents are not a usable signal here: a provisional `SetQueue` preserves the previous queue, so a discarded response and an applied one can look identical. Splitting the freshness counter into separate playback and queue halves was tried first and reverted — both halves carry the current track, so per-half checks let a stale queue response reinstate a track that a live playback callback had already moved past
- The Web API bootstrap no longer runs twice on every launch. The reconnect handler treated any rise to ready as a reconnect and re-fetched playback state, guarded only by `wasConnectionReady` still being nil — which never held, because `connectionState` is a `CurrentValueSubject` and delivers its seed the moment the view subscribes, so the first real transition was never the first callback. The startup task fetches the same thing moments later. A reconnect is now recognised as what it actually is: a drop followed by a rise
- Logging out now tears the librespot session down instead of only clearing the token. `AuthViewModel.logout()` cleared Keychain and memory and left Rust untouched, so the Spirc connection stayed registered on Spotify Connect for the account that had just logged out — and with no shutdown flag set, the recovery loop treated the next network hiccup as an outage worth fixing and re-announced the device. A confirming log showed exactly that: 30 seconds after logging out mid-outage, `active device is <spotifly_…>`. Logout now says goodbye and then releases Session, Player, Mixer and Spirc, which also invalidates the session generation. Several orderings had to be closed around it: the teardown is awaited before the auth state is cleared, so no login can start a rebuild while one is going down; `spotifly_shutdown` publishes the disconnected snapshot itself rather than waiting for the listeners, since a snapshot still claiming a ready Spirc is what let Swift adopt the dead session as healthy; an initialization overlapping a logout is neither cancelled (`waitUntilReady` swallows cancellation and would spin on the main actor) nor waited for (a stalled setup would hang the logout) but invalidated by a lifecycle generation, checked on both the success and the failure path because the superseded attempt reports failure while leaving a live session behind; a rebuild finishing during a teardown clears what it built, shutting down through its own Spirc handle because a cleanup may already have nilled the global one; and no initialization may start while a logout runs
- Removed a duplicate `stop()` on logout. `LoggedInView` passes `handleLogout` as `onLogout`, which already stops playback, and the profile view's own closure called `stop()` again before invoking it — visible in the logs as `spotifly_stop called` twice, two milliseconds apart. Idempotent, so harmless, but the second call was pure noise
- Fixed a deadlock that could hang the app during a reconnect. `AudioRenderer.stop()` stops the consumer but never signalled the semaphore a blocked writer waits on, so if the ring buffer happened to be full at that moment, `writeAudioData` looped on 500 ms timeouts waiting for space nothing would ever free. The caller is librespot's player thread, so the teardown froze at `Shutting down player thread` and never completed. Latent before, but reachable on every reconnect since the audio-throttle fix started sending a stop when the Player is torn down — *before* it is dropped, while it may still be writing. `stop()` now wakes the writer, and the writer gives up instead of waiting when the renderer is no longer rendering, dropping audio destined for a renderer that has stopped
- The playback position no longer runs ahead while the connection is down. Two clocks were extrapolating: Swift interpolated from an anchor, and `spotifly_get_position_ms()` separately added wall time since the last Player event, capped at exactly 5000 ms. When a reconnect tore the Player down, `POSITION_MS` froze but `IS_PLAYING` stayed true, so Rust kept returning `last + 5000` — while rehydration correctly resumed from the raw value, surfacing the gap as a five-second backwards snap. Rust now reports only what the Player last said (it emits updates every 200 ms, so the removed extrapolation added no smoothness), and Swift is the sole display interpolator, advancing only while the connection is ready and freezing at the real position when it drops. The once-a-second drift check also compares even when Rust's value did not change — a frozen value is exactly when the old "only if it changed" guard suppressed the correction that was needed. Two latent bugs fell out along the way: the drift computation could trap on `Int32` overflow, and the position was clamped to zero whenever the track duration was not yet known
- Swift now adopts a recovery that Rust completed on its own. If an explicit initialization failed after the Rust session had been created, `isInitialized` stayed `false` — and when the health check or reconnect loop later rebuilt Rust successfully, nothing told Swift. The next play would call `initializeIfNeeded`, whose `SpotifyPlayer.initialize` starts with a `cleanup()`, tearing down the session that had just been restored. `PlaybackViewModel` now watches the connection snapshot and marks itself initialized (clearing the stale error) when Rust reports connected and Spirc-ready while no explicit initialization is in flight. It deliberately does **not** clear the flag on a not-ready snapshot: transient disconnects belong to Rust, and dropping the flag there would send the next user command straight back into a destructive Swift rebuild
- Removed the Swift reconnect watchdog, which could permanently disable Rust's recovery. After 120 seconds without a ready connection it ran a destructive cleanup-then-init: the cleanup invalidates the generation, so any reconnect loop working the problem abandoned, and if the single init attempt then failed because the network was still down, nothing was left retrying — no loop, and no new watchdog either, because arming one requires a ready-to-not-ready transition and the state was already not-ready. The session health check did not rescue it: it triggered on `Session::is_invalid()`, a flag only set by `shutdown()`, so a session created by a failed init reports itself valid forever. Recovery now belongs to Rust alone, which retries unbounded. Two supporting fixes: the health check now triggers on "not connected and nobody is recovering" rather than only on invalidity, which also closes the same trap at startup when the very first initialization fails; and system wake asks Rust to reconnect instead of rebuilding from Swift, falling back to a full rebuild only when there is no session to reconnect to (after a logout, or when initialization never succeeded). Soft reconnect kept the Player alive across sessions to avoid an audible gap, but a Player outliving the Session it was built for is what forced most of the surrounding complexity: the librespot patch making Spirc adopt an orphaned `play_request_id`, a context reload after every reconnect (with its seek-to-position blip), and a watchdog that re-issued play commands when the audio key fetch on the dead session silently timed out. Run with `cargo test` in `rust/`

### Fixed
- Logging out drops what was playing, so the next account cannot resume it. `spotifly_cleanup` reset the whole playback lifecycle — playing, position, resume point, shuffle, repeat, volume, active device — but left `CURRENT_TRACK_URI` and `CURRENT_CONTEXT_URI` behind, and those two are exactly what `resume_via_load` loads: the context, with the track as its hint. Nothing after a login rewrites them until playback establishes something new, because `update_current_context_uri` ignores empty values and the track URI is only ever written from player events. So pressing play as a freshly logged-in account reached an activated Spirc with no queue, `play()` produced no `Playing` event, and the fallback loaded the previous account's context — reachable through the ordinary control path, where `sendTransportCommand` takes the Web API's no-active-device 404 and falls back to `spotifly_resume`. The same hole in `RESUME_POSITION_MS` was closed one commit earlier, which is what left this as the position's target with no position. Only the full cleanup clears them: the wake and reconnect paths run `do_reconnect_cleanup`, which deliberately leaves playback state alone so the rehydrating load has something to reload. Logout and an explicit rebuild are the cases where Rust genuinely has no track or context loaded afterwards — which Swift already assumed, since `performInitialization` nils its own `currentTrackUri` for that reason
- A stale cluster timestamp no longer parks the progress bar at the end of the track. Both paths that anchor a position from a timestamped snapshot back-date the clock by the elapsed time, so interpolation reports the current position rather than the measured one — correct and necessary while monitoring a remote device, where `position_as_of_timestamp` plus elapsed genuinely is where that device is now. The Web API path discarded that compensation when it would carry the position past the end of the track; the Mercury path did the same arithmetic with no such bound, so a sufficiently old cluster update anchored the clock minutes in the past and the bar sat pinned at the track end while the remote device played on. Staleness is a property of Spotify's timestamp, not of the endpoint that delivered it: cluster updates forward `player_state.timestamp` unchanged and it can be minutes old, while local callbacks stamp the current time and compensate by nothing. Both paths now share one `positionAnchor(forPosition:takenAt:)`, which also removes the duplicated arithmetic. Clamping the compensation to land exactly on the track end was considered and rejected — `clampedToTrack` already bounds the display, so it looks identical to no guard at all, tidying the arithmetic without changing what the user sees; discarding shows a genuinely measured position that is merely behind and that the next update corrects. The bound reads `trackDurationMs`, so it is by construction the same length the display clamps against
- Resuming after the device stopped being active continues the track instead of restarting it. `resume_via_load` seeks to `POSITION_MS`, and `PlayerEvent::Stopped` zeroed that — while librespot sends `Stop` to the Player on every deactivation, from `handle_disconnect`. The resume point was therefore destroyed at deactivation, potentially minutes before anything asked to resume, and playback came back from 0:00. One global was serving two meanings that disagree here: where the Player is now, for which zero is right once it has stopped, and where playback should pick up, which has to survive a stop. `Stopped` still resets the live position, because that event cannot say why playback stopped — `handle_stop` runs for a deactivation, for a queue that has run out, and for `prev` at the first track, and keeping the position for all of them would make `next` on the last track leave a resume point mid-track, so pressing play afterwards restarted it there instead of from the beginning. The resume point is instead captured where the cause is known: the `SessionDisconnected` arm, which librespot emits from `handle_disconnect` just before the `handle_stop` that follows it. It is cleared once playback is running again and consumed by the resume path, so it can never outlive the deactivation it belongs to. This removes a wart rather than adding one — `freezePositionForDisconnect` already carried a workaround for Rust reporting zero after a teardown, and two other readers improve as well: the drift check's playing-state sync now lands on where playback really stopped, and the position published alongside shuffle/repeat changes no longer clobbers Swift's anchor with a zero, which is what overwrote a correct 12087 ms in the confirming log
- The French tooltip on the scroll-to-current-track toolbar button said "Ouvrir la file d'attente" ("Open the queue"), a copy of the `queue.open` translation four lines above it in `fr.lproj/Localizable.strings`. It now reads "Aller au titre en cours". The rest of the French `queue.*` group matches English
- Only one resume runs at a time. `Spirc::play` only queues a command, and `spotifly_resume` waits half a second for a `Playing` event before falling back to loading the saved context and waiting two more — while Swift dispatches each press to its own detached task. Pressing play repeatedly, which is precisely what an unresponsive play button provokes, therefore stacked several play-then-load sequences, each capturing the position at its own moment and restarting the track there. `IS_PLAYING` did not cover the gap, since it stays false until the first sequence produces audio. A resume already in flight now reports success to later callers instead of starting a second one, which also closes the same race on the path where Spotifly is already the active device
- The Now Playing bar's queue counter no longer reads one past the end. `currentIndex` is `previousTracks.count`, which sits one beyond the last item whenever the queue holds history but no current track — a state a queue reaches simply by playing out, and the state the sleep-wake queue wipe left behind — so the label rendered `9/8`. The index is honest; the sentence was not, because "track n of m" needs an n. The counter is now shown only while a current track exists; the button keeps its slot and shows the queue glyph instead, since the counter was its only label and dropping it outright would have left an invisible control that VoiceOver announces unnamed. It also gained a tooltip and an accessibility label, which it never had. `QueueListView` needed no change: it uses the same index for the played/pending split, where treating every entry as played is correct when none is current, and its scroll-to-current already guarded the bound
- Transport controls work again when no device is active anywhere — most visibly, the play button after waking from sleep, which could not resume a paused track at all. `sendTransportCommand` routed on `isActiveDevice`, a two-valued flag standing in for a three-valued fact: Spotifly is the active device, another device is, or nobody is. It read the third case as the second and sent the command to a Web API with no device to deliver it to; Spotify answered 404, `throwAPIError` flattened that into a generic `apiError`, and it landed in an `errorMessage` nothing displays — so each press produced one request and no playback. Sleep reaches that state through Spotifly's own teardown: `spotifly_disconnect` shuts Spirc down, librespot answers any shutdown with `SessionDisconnected`, and its handler clears the active flag, so the wake path captures `was_active: false` and rebuilds passively. 404 from the player endpoints is now its own `noActiveDevice` error, and a transport command that hits it falls back to the local player, which takes the Connect role on the way through: `spotifly_resume` activates and then reloads the saved context at the saved position. Activating first is a precondition rather than a nicety — `SpircTask` matches `_ if !self.connect_state.is_active()` ahead of every transport command, so `Play`, `Load`, `Next`, `Prev`, `Shuffle` and `SetPosition` are discarded with a warning while inactive, and the resume path including its load fallback would have been dropped in silence. The same catch-all exposed a latent trap in `resume_via_load`, which recorded the device as active whenever `Spirc::load` returned `Ok` — but `Ok` only means the command reached the channel, so a discarded load looked like a successful takeover and left Swift routing every later command to a local player that was ignoring all of them. Activity is now recorded only where it is actually established, never inferred from a queued command. What this recovers is resume, which is also the only one that needed recovering: with nobody active there is no context loaded and no track playing, so pause, next, previous, seek and shuffle reach an inactive Spirc and are correctly dropped — there is nothing to pause or skip. Activating for those would take the Connect role from the user's other clients to accomplish nothing, and making them work would mean silently starting playback in response to "next" or "seek". Two alternatives were rejected: re-activating unconditionally on wake fixes only the sleep path and would take the Connect role back from a phone that legitimately took over while the Mac slept, and publishing the cluster's active-device id in the connection snapshot adds a second piece of cluster state to keep accurate across every rebuild — `LAST_ACTIVE_DEVICE_ID` shows the trap, since it is a notification latch that is never cleared on reconnect and afterwards holds a stale *own* device id that would read as "a remote device is active"
- Waking from sleep no longer empties the queue. The reconnect that follows a wake re-bootstraps from the Web API, and with no device active Spotify answers both `/me/player` and `/me/player/queue` with 204 — which decodes to a nil playback state and an empty queue, indistinguishable from a genuinely empty one. That is the absence of an answer, not an answer that nothing is queued, and applying it was worse than it looked: `setQueue`'s `previous: nil` contract preserves the history and overwrites the rest, so the pending tracks — the one part no later callback reconstructs — were destroyed, together with the current pointer, which `Queue.reconciled` then could not repair because it can only re-split a list that still contains the track. The result was a Queue section showing only played tracks while the Now Playing bar still showed the paused track, since the bar is fed by a response that was nil and therefore never applied. A bootstrap response carrying no playback state, no currently-playing track and no queued tracks is now recognised as carrying nothing and leaves the queue untouched
- Navigation now has one route value and one back/forward history across sidebar sections, library selections, search results, and stack drill-downs. Native stack pops share the toolbar's Back semantics; every user navigation is replayable; deleted entities and evicted bounded search queries are invalidated across the whole history; and clearing the search field preserves its cached, query-keyed result route
- The queue's current pointer now follows the logical track that is actually playing instead of the stale split from librespot's initial `SetQueue`. Spotifly preserves the reported ordering, finds the nearest matching occurrence in either direction, and re-splits whenever either playback URI or queue data arrives; starting deep in an album, automatic transitions, next, and previous therefore keep the position indicator, played-track dimming, remaining count, and scroll target aligned without a Web API refresh
- Web API track relinking now preserves the originally requested track as Spotifly's identity. `linked_from` supplies the stored ID and URI while the playable replacement still supplies its metadata; field-projected responses request that reference explicitly, supported endpoints request the user's market, and playback bootstrap data follows the same identity rule. Playlist/search results, queue hydration, Now Playing, favorites, and playlist writes therefore agree on one logical track instead of caching or sending Spotify's market-specific alternative ID
- The app no longer runs two `AppStore` instances. SwiftUI calls a View's `init` repeatedly but keeps only the first `State(initialValue:)`, and `LoggedInView.init` did two things that outlived that discard: the services subscribed to the global player subjects inside their own initialisers, and `setStore` mutated the shared `PlaybackViewModel`. The discarded `QueueService` therefore kept handling every Spirc notification against its own empty store — re-fetching all queue metadata on each one — while the shared view model ended up reading that discarded store, so the macOS Now Playing panel and the in-app bar resolved against different data. `QueueService`, `ConnectionService` and `DeviceService` now construct inert and are started by an idempotent `activate()` from the surviving view's lifecycle task, alongside `setStore`, so construction has no observable effect however often it runs
- Track metadata is fetched in one request instead of one per track. `SpotifyAPI.fetchTracks` fanned out to a `/v1/tracks/{id}` GET per ID through a task group, so hydrating an 18-track album queue issued 18 requests — the batch endpoint `/v1/tracks?ids=` takes 50 at a time. The 50-ID chunking moved down into the API layer, where that limit comes from; `TrackService` no longer splits IDs it has no reason to know the cap for. Spotify answers positionally with `null` in the slot of an ID it has no track for, which the response is zipped back onto, so an unavailable track cannot shift the tracks after it onto the wrong IDs
- A logical current track that is not yet in `AppStore` now recovers its title, artist, artwork, and duration without waiting for another queue callback. Queue hydration and Now Playing recovery share one per-track in-flight registry in `TrackService`, so overlapping batches do not duplicate requests; cache hits avoid token work, caller cancellation does not cancel useful shared loading, and failed requests can be retried. A track Spotify answers without — one that does not resolve for the user's market — is remembered as absent rather than re-requested on every queue update, while a request that failed outright still retries
- Relinked Spotify tracks now keep their logical context identity throughout playback instead of replacing it with librespot's playable-alternative ID. The in-app and macOS Now Playing surfaces therefore resolve the same normalized track metadata, favorite state, artwork, resume hint, and radio position while still using the decoded audio item's authoritative duration. Track changes also clear the previous stream duration and stale system metadata before adopting the new track, preventing a previous title or cover from being paired with the next track's timing
- Albums that opened with a header and no tracks now load. Every album, artist and playlist detail fetch ran *inside* the view's `.task`, so SwiftUI cancelling that task on teardown cancelled the request — and the resulting `URLError.cancelled` was rendered as the album's error, the red `Abgebrochen` under the play button. Teardown was routine: the detail router picked between an `init(album:)` and an `init(albumId:)` depending on whether the entity was in the store yet, and those are the two branches of a `_ConditionalContent`, with structural identities that `.id()` does not unify, so the moment another producer inserted the entity SwiftUI destroyed the view that was fetching it. A second caller that arrived meanwhile fared worse: `AlbumService` waited for the first by polling a flag every 50 ms, read the flag's disappearance as success, and returned an empty track list with no error and no retry, so the album stayed blank until you navigated away and back. Fetches now run in an unstructured task owned by the service (`InFlightRequests`), which a cancelled caller does not take down with it; the result lands in `AppStore` and the view that replaced the cancelled one reads it there. Detail views read the store rather than keeping their own `@State` copy, so there is one branch and one initialiser, and a cancellation is no longer shown as a failure
- Every section fetches each thing once. `AlbumService.fetchAlbumDetails` had no in-flight deduplication at all and two entry points into it (`loadAlbum` then `loadTracks`), `ArtistService` had none of any kind, and `PlaylistService` had a per-ID task map that only covered one of its paths — three sections, three different answers. All of them now go through one keyed single-flight registry, as do the four library list loads, which were four hand-written copies of the same stored-task dance
- Opening an album no longer re-fetches metadata the app already has. `/albums/{id}` was requested beside `/albums/{id}/tracks` even when the album had just come from the library list, an artist page or a search result; the same for playlists. Albums carry an explicit `detailsLoaded` marker now — presence alone is not enough, since `TopItemsService` synthesises a stub from a track's album object — and only the missing half is requested. An artist's discography is cached in the store instead of living in the view's `@State`, where it was re-fetched on every visit, and the detail views ask `/me/tracks/contains` only about tracks whose status is not already known
- An album or playlist that genuinely has no tracks is no longer re-fetched forever. `tracksLoaded` was defined as `!trackIds.isEmpty`, so "loaded and empty" was indistinguishable from "never loaded" — including for a playlist the user had just emptied. It is now set by the load, whatever came back
- A failed reorder actually rolls back. The rollback re-read the playlist "from the server" through a cache-respecting call, which saw a loaded playlist and returned the optimistically reordered list it was supposed to undo, without issuing a request. It now re-fetches the tracks, and says so when even that fails
- A track or album list that fails to load can be retried. The retry button lived in a branch only reachable while the entity itself was missing — which it usually is not, since the list you clicked from put it in the store — so a failed track list showed bare red text, and a failed artist discography showed nothing at all
- Nothing is asked for twice, and nothing is asked for that is already known. An album opened from a search result re-fetched metadata the search had already returned, because `SpotifyAPI+Search` builds its albums with the memberwise initialiser and so inherited the "details not loaded" default; `detailsLoaded` has no default any more, so a producer has to say what it knows. Two views wanting the same track's favorite status in one frame both asked, since the resolved-status cache is only written when a check returns — they now join one cancellation-resilient in-flight request, so replacement views cannot miss the result either. Returning to a search re-asked about the same tracks, because search, the search track list and the queue used the deliberately cache-ignoring `refreshFavoriteStatuses`; only the now-playing bar keeps it, as the single place where a track favorited in another Spotify client can still surface. And the loading paths no longer fetch an access token before deciding whether they need one: the services hold a token provider, as QueueService already did, so a cache hit touches the session not at all — opening one album used to log sixteen token fetches that led to no request whatsoever
- A pull-to-refresh no longer races the load it replaced. Cancellation is cooperative, so a superseded run whose response had already arrived went on to write its page over the refresh's reset and to clear the loading state the replacement had just set. Superseded runs now check before writing. In the same family: a reorder whose reconciliation was cancelled by a newer reorder was read as a failed reorder, and rolled back over the newer one

- A reconnect no longer reports success before playback is actually back. `Spirc::load()` only queues a command, so the rehydrating load could be accepted and then never take effect, leaving a session that reads ready but plays nothing — and Swift's Web API bootstrap could land in the gap between the load and playback resuming. The result is now acted on rather than logged: a closed command channel fails the attempt so the loop builds a fresh session, while absent resume metadata (reachable when an outage lands between a play command and the events that record what is playing) is not treated as a failure, since that would make every later attempt fail identically forever. On success the rehydration waits up to three seconds for the Player to actually start before readiness is announced. Connection success — ready flags, connected-since, backoff reset — is now committed once at the very end rather than when Spirc is created, so no intermediate snapshot can announce a session that cannot yet play and a failure leaves the previous disconnected state untouched. The commit is skipped if the initialization was superseded or a teardown started while it waited
- Whether an outage resumes playback no longer depends on event ordering. The reconnect task read `IS_PLAYING` and the active-device flag when it *started*, but between the disconnect and that moment the deactivation handler clears the active flag, a `Stopped` event clears playing, and a final cluster update can clear both — so a real outage could come back silent and passive purely because the events arrived in an unlucky order. The intent is now captured at each of the five recovery triggers, before anything clears it, and passed explicitly into the loop as a `RecoveryIntent`
- A superseded listener can no longer overwrite current state. Both long-lived Rust listeners now check their generation before processing anything: the player event listener only guarded its `SessionDisconnected` arm, so every other event — position, playing, track change, active device — still applied; the cluster listener checked only *after* its stream ended, leaving every message before that unguarded. Replaced listeners drain asynchronously after their successor is live (the logs show them delivering seconds later), so both could write state belonging to a session that no longer existed. The guard skips only when an event is actually present, so a closed channel still reaches the shutdown path instead of spinning
- The playback position no longer jumps to a stale value and back after a reconnect. Readiness was published the moment Spirc existed, while activation and the rehydrating load still had to run. Swift reacts to that publication by bootstrapping from the Web API, so it fetched and applied a server snapshot — in one measured case 145010 ms with a timestamp 144 seconds old — which Rust then overwrote 300 ms later with the real position of 99240 ms. `init_player_async` now builds a complete session and publishes its readiness exactly once, at the end: Spirc created, device activated, playback rehydrated, *then* announced. The activation path records its state without publishing (`store_active_device`) for the same reason, since publishing between activation and rehydration would reopen the same window. Chosen over the alternative of having Swift skip the Web API when playing locally, because that keys off state which is still settling at that moment — activation lands 483 ms after the bootstrap fires — and it would still have gone wrong for a track that was paused when the outage hit
- Playback no longer races after a reconnect. `AudioRenderer` paces the decoder by comparing audio written against wall clock since an anchor, because `AVSampleBufferAudioRenderer` accepts data eagerly and provides no real-time back-pressure. That anchor is reset in `start()` — but `start()` returns early when it is already rendering, and dropping the `Player` during a rebuild never ran `Sink::stop`, so the renderer kept believing it was rendering and the anchor survived the whole outage. On resume the throttle saw a large accumulated deficit, never slept, and let the decoder run flat out: measured at ~40 seconds of audio in under one second. Playback still *sounded* continuous because the renderer plays its buffer out in real time, but `EndOfTrack` fired ~40 s early and Spirc advanced the track with the audio still playing. Fixed on both sides — Rust now sends a stop when tearing a player down, and `start()` re-anchors the throttle even when it returns early (only the anchor, since a full pipeline reset mid-playback would glitch the audio)
- A dead session is now noticed even when Spotifly isn't the active device. Every existing recovery trigger needs something to happen: the cluster listener only acts when its stream *closes*, and librespot's dealer retries internally so that stream can stay open for minutes past a dead session; the zombie check in `require_session_connected` only runs when a command is issued. While Spotifly is playing, something trips one of those within seconds. While playback is on another device, nothing does — no commands are issued, so nothing calls `mark_disconnected`, so the published snapshot still reads "connected" and the Swift reconnect watchdog never arms either. Observed in testing: after a real outage with playback on a phone, the session stayed silently dead for 1m43s and only recovered because the machine happened to sleep and wake. A periodic check now polls `Session::is_invalid()` once a minute and starts the normal recovery when it finds a dead session. It costs one sleeping task per session generation waking once a minute to read two booleans, and exits when its generation is superseded, so it dies with the session it belongs to
- Playback now actually resumes after a reconnect. The rebuilt Player has no track loaded, and nothing else loads one — Spirc coming up ready and the device becoming active again only makes it *available* to play. So the session returned healthy and completely silent, while the UI kept showing the pre-outage track and position because `IS_PLAYING` and the position anchor survive the rebuild. The recovery path now issues one deterministic load of the captured context, seeking to the captured position, when playback was local and running before the outage. This replaces a five-second "auto-resume" window that waited for a `Paused` event on the assumption that the track would load itself via `transfer(None)` — nothing in that path ever called `transfer(None)`, so the event never arrived and the window did nothing. It went unnoticed because the rebuild was previously only the fallback for a failed soft reconnect, which kept the Player playing on its own
- Automatic recovery from a network outage now actually retries. Two bugs, both found by unplugging ethernet mid-playback. First, the reconnect loop invalidated itself: each attempt calls `init_player_async`, which bumps the session generation *before* it can fail, so the loop's supersede check compared against the value captured at loop start, saw its own rebuild as a foreign takeover, and abandoned after a single failed attempt — with the Player already torn down by the preceding cleanup, playback then stayed dead for the whole outage. The loop now adopts the generation its own attempt produced, so only genuinely foreign rebuilds and teardowns stop it. Second, the schedule was a fixed ten attempts totalling about three minutes, after which the loop exited entirely; any longer outage left nothing running to notice the network returning, and only the Swift watchdog's 120-second forced reinitialize — or a manual play — could recover it. Backoff now caps at 30 seconds and keeps retrying. This is not idle polling: the loop exists only while disconnected and exits on any lifecycle event, since every iteration re-checks the generation and the teardown flags
- Recovery is now generation-safe, closing a race where Swift and Rust could end up on different session generations. Two problems: the player event listener's stale-session check compared `EVENT_LISTENER_GENERATION` against `SESSION_GENERATION`, but the former was written to the latter's new value on every bump — so the two were always equal and the check could never reject anything. And the reconnect loop was guarded only by a `RECONNECTING` flag, which says "a loop is running", not "the thing it is fixing still exists": it could sleep up to 30 seconds between attempts, wake after a manual restart or a logout had already rebuilt or torn everything down, and rebuild over the top with a stale token. Each listener now captures its own generation (possible only because a rebuild replaces the listener along with its session — the old global existed because soft reconnect kept one listener alive across sessions), the reconnect loop abandons if its generation moved or a teardown started, checked both after each backoff sleep and after the token round-trip, and `spotifly_cleanup` invalidates the generation up front so anything in flight notices. `EVENT_LISTENER_GENERATION` is gone. Five new unit tests cover the rules
- Fixed a "Publishing changes from background threads is not allowed" runtime warning, and the thread-safety hole behind it. The Combine subjects bridging Rust callbacks into Swift are `nonisolated(unsafe)` globals reached from Rust's own threads, and only three of the eleven callbacks hopped to the main actor before sending — the other eight relied on every subscriber remembering `.receive(on: DispatchQueue.main)`. That unwritten invariant broke as soon as a SwiftUI `.onReceive` subscribed to the connection snapshot, because `.onReceive` delivers on whatever thread the publisher emits on. All non-audio callbacks now hop first, which also closes a real hazard a subscriber-side hop never could: several Rust tasks (player event listener, cluster listener, reconnect loop) can publish concurrently, and Combine subjects are not safe against concurrent `send` — `.receive(on:)` hops only *after* the subject has already delivered. Audio data keeps its separate real-time-safe path
- Initialization no longer reports success before the player is usable. `PlaybackViewModel` set `isInitialized` as soon as the FFI initializer returned, then polled `isSpircReady` for five seconds and ignored the timeout — so Swift could permanently believe the player was up while every Connect command failed, and `initializeIfNeeded` would then refuse to retry because the flag was already true. Readiness is now the authoritative condition (session connected **and** Spirc ready), a timeout is treated as failure, and the flag stays false so the next caller retries. On the Rust side, `spotifly_init_player` no longer falls back to a bare `session.connect()` when Spirc initialization fails: every Spotifly control goes through Spirc, so a connected session without one is not a player, and returning success for it was what made the unusable state permanent
- A stale Web API response can no longer overwrite newer state from Rust. `fetchInitialPlaybackState` fetched playback and queue data and applied both unconditionally when the requests completed, but Rust callbacks can arrive while those requests are in flight — so after a reconnect or transfer Swift could briefly show the correct live state and then replace it with an older network snapshot. `AppStore` now carries a monotonic `liveStateRevision` that is bumped whenever authoritative playback or queue state from Rust is accepted; the bootstrap captures it before issuing its requests and discards the response if it moved. One counter covers both playback and queue: it is coarser than tracking them separately, but the only cost is occasionally dropping bootstrap data that the live callbacks are already replacing. Provisional `SetQueue` notifications deliberately do not bump it, since they carry no usable queue and the Web API refresh they schedule must not be treated as stale. This replaces relying on the Web API `timestamp`, which was only ever used to compensate the position anchor *within* a response and was never compared against anything Rust had published
- Whether Spotifly is the active Connect device is now one derived fact instead of two competing ones. Rust tracked it in an `IS_ACTIVE_DEVICE` atomic written from fourteen scattered command and event sites and never reconciled against the cluster, while the cluster listener separately pushed the active device ID to Swift's `AppStore` — so playback routing (which read the atomic) and the views (which read the store) could disagree about whether Spotifly or a remote speaker was active, especially around external transfers. The cluster listener now computes `is_active = cluster.active_device_id == own_device_id` (the same comparison `SpircTask` makes internally) and publishes it in the connection snapshot, so both readers see the same value. Also: an empty active-device ID is no longer dropped, so "nothing is playing anywhere" clears the state instead of leaving the last active device shown forever; and `PlayerEvent::Stopped` no longer clears active-device state, which had made local playback simply ending look like a remote device taking over
- Swift no longer drives reconnection or Web API refetches from Connect activation. The two FFI callbacks are renamed to what they actually report (`spotifly_register_became_active_callback` / `..._became_inactive_callback`, surfaced as `SpotifyPlayer.becameActive` / `.becameInactive`), and `LoggedInLifecycleModifier` now keys off readiness transitions in the connection snapshot instead. Previously the activation callback triggered a full `fetchInitialPlaybackState`, so **every** device handoff fired an unguarded Web API bootstrap that could overwrite live Rust state — the most likely cause of Swift and Rust disagreeing about what was playing — while the deactivation callback armed a watchdog that would force a full reinitialize. Both now fire only on genuine connect/disconnect transitions, and the initial rise to ready is skipped because startup already bootstraps once
- The deactivation callback no longer doubles as a reconnect-failure signal. It was fired both by Spirc (meaning "another device took over", immediately) and by the reconnect loop after all ten attempts were exhausted (meaning "recovery gave up", late), so one callback carried two unrelated meanings with wildly different timing. Exhaustion is now reported only through the connection snapshot, which already carries `last_error` and the attempt count
- Handing playback off to another Spotify device no longer looks like a network outage. librespot emits `SessionDisconnected` when the local Connect device becomes **inactive**, not when the session fails — `SpircTask::handle_disconnect()` runs on an explicit disconnect, on shutdown, and on any cluster update that gives the active role to another device (this is upstream behavior, not part of the Spotifly patch). Rust treated every one of those as a dead session: it marked the connection disconnected and started a reconnect loop against a perfectly healthy session, so playing to a phone or speaker could show a disconnected UI and fire an unnecessary reconnect. The event now updates active-device state only, and recovery starts solely from real transport evidence — a `Session` that reports itself invalid, the cluster/dealer stream ending, or an explicit force-reconnect. The session-validity check preserves the one genuine failure this event does report (librespot calls `handle_disconnect` when the Spirc task shuts down unexpectedly, which the cluster listener can miss while the dealer stream is still open)
- The connection snapshot's "connected" facts now come from the point where the connection is actually established. `connected_since_ms`, the reconnect backoff counter, and `last_error` were reset in the `SessionConnected` handler, which fires on Connect *activation* and can happen repeatedly over one healthy session; they now reset where the session and Spirc are created. `SessionConnected` only records the connection id and marks the device active
- Player initialization and restart are now serialized through one stored `Task`. `forceReinitialize` and `initializeIfNeeded` both ran `SpotifyPlayer.initialize`, which performs a Rust cleanup followed by a rebuild — and `@MainActor` prevents them running simultaneously but not overlapping, since every `await` is a suspension point another caller can enter. Two overlapping calls could interleave one call's cleanup with the other's rebuild, leaving Swift holding state for a Rust generation that had already been replaced. Late callers now await the in-flight run instead of starting a competing one, which also coalesces the genuinely concurrent triggers: system wake and the reconnect watchdog can fire together, and one rebuild is the correct response to both. The two near-duplicate bodies collapsed into one, and `isInitialized` is cleared up front so a restart whose `initialize()` throws no longer leaves the flag stuck true
- Playback commands no longer report success for actions Rust rejected. Three paths bypassed the connectivity guards that `next`/`previous`/`pause`/`resume`/`toggleShuffle` already had: `togglePlayPause` called the unguarded `SpotifyPlayer.pause()` FFI wrapper directly and asserted `isPlaying = false` itself (instead of routing through the view model's guarded `pause()`, which also carries the Web API fallback for remote devices and leaves the flag to the Mercury callback); `stop()` cleared track and playing state even when the session was down; and `performSeek` had no guard at all, so during a short outage the progress bar stayed parked at a position playback never reached. `performSeek` now re-syncs the anchor from the real position when the command can't be sent, which keeps scrubbing feedback immediate without lying about the result
- Transferring playback to another device no longer reports success unconditionally. `DeviceService.transferPlayback` optimistically marked the target active and returned `true` while the FFI call ran detached and its `SpotiflyResult` was discarded, so a rejected transfer (no session, invalid session, SpClient failure) left the device list showing a device that never became active. The two transfer wrappers now return whether Rust accepted the command, and a rejected transfer rolls the optimistic update back to the previous active device and returns `false`
- Opening a playlist no longer fails for newer/stricter Spotify developer accounts. `fetchPlaylistTracks` was still calling the deprecated `GET /playlists/{id}/tracks` endpoint, which Spotify now rejects with `403` for apps approved after the API tightened — `fetchPlaylistDetails()` would succeed but the tracks fetch failed, so the whole playlist appeared broken even though the playlist list loaded fine. Switched to `GET /playlists/{id}/items` (the documented replacement) and added pagination via the response's `next` URL, since the new endpoint caps at 50 items per page versus the old endpoint's 100
- Opening a playlist for the first time no longer occasionally fails with a cancellation error. `PlaylistDetailView` lives in the list+detail split that appears when Playlists switches from 2 to 3 columns, so the detail view could be recreated mid-fetch, re-triggering its `.task` and firing a second, untracked `fetchPlaylistDetails` request; when the original view was torn down its in-flight request was cancelled and the surviving view surfaced that as an error. `PlaylistService.fetchPlaylistDetails` now dedups in-flight requests per playlist ID via a stored `Task` (matching the pattern used by `AlbumService`/`ArtistService`/`PlaylistService`'s own user-playlists load), so a re-triggered `.task` awaits the existing request instead of racing a new one
- Playlist, album, and artist rows in the sidebar lists are now clickable across their full width instead of only over the cover art and label. The rows were full-width `Button`s with `.buttonStyle(.plain)`, but on macOS that style's hit-testing doesn't reliably honor `.contentShape(Rectangle())` over a transparent `Spacer()` region — clicks only registered over the actual rendered image/text content even though the row's layout and selection highlight already spanned the full width. Replaced the `Button` wrapper with a plain `HStack` plus `.onTapGesture(perform:)`, which does respect `contentShape` consistently
- Restored the always-visible search field in the top toolbar. A previous refactor had switched it to the `.searchable(text:isPresented:)` variant, which hides the field unless `isPresented` is true (and it defaulted to false), so the field had disappeared. It is again attached to the `NavigationSplitView` as a plain `.searchable(text:)`, visible in every section
- Reworked the logged-in window layout to an Apple Music-style hierarchy: a single, stable two-column `NavigationSplitView` (sidebar | content region). The 2- vs 3-column variation now happens *inside* the content region (a single section view, or a list + detail `HSplitView`), so the sidebar column is never recreated — its width stays put across every section switch and no longer snaps between per-layout defaults. The now-playing bar is overlaid on the content region, so it centers over column 2 (or columns 2+3) without the previous sidebar-width math
- Volume changes during local playback now take effect immediately instead of lagging by up to ~2 seconds. Volume was applied by librespot's software mixer in Rust, baking the gain into PCM that then sat in the render buffer, so changes were only heard once that buffer drained. The Rust player now uses `NoOpVolume` (no sample attenuation) and gain is applied at the output via `AVSampleBufferAudioRenderer.volume`, which scales audio as it plays. The slider value is passed through librespot's default logarithmic taper (`VolumeCtrl::Log`, 60 dB) so the perceived curve is unchanged, and the soft mixer still tracks the logical volume so Spotify Connect reporting and remote volume control are unaffected
- Favorites no longer intermittently render the empty "No favorites yet" state despite the `/me/tracks` request firing. The load was tied to the Favorites view's `.task`, so when the view was recreated (navigation/column-layout change) mid-request the in-flight load was cancelled, and a recreated view's `.task` could observe `isLoading == true` and bail — leaving the list stuck empty until a manual refresh. `TrackService.loadFavorites` now uses the stored-unstructured-`Task` dedup pattern (matching `AlbumService`/`ArtistService`) so the load survives caller cancellation, and `TrackService` is persisted via `@State` in `LoggedInView` so the in-flight task reference survives view recreation
- Handle Spotify's upcoming refresh-token expiration (refresh tokens expire after six months starting July 20, 2026): `invalid_grant` responses are now detected as a distinct `SpotifyAuthError.tokenRevoked`, the stored token is discarded instead of retried, and an expired/revoked token mid-session now invalidates `SpotifySession` and routes the user back to the sign-in flow rather than silently looping on a dead access token
- Starting song radio from the currently playing track now seeks with the same interpolated playback position the UI uses, avoiding stale-position jumps when the radio context loads
- Fixed the Now Playing overlay (menu bar) not updating when a song auto-advances during album/playlist playback
- Favorites now resolve via batched `/me/tracks/contains` checks for the tracks actually shown in album, playlist, queue, search, and now-playing views instead of depending on a full favorites preload
- Saving and removing favorite tracks now uses Spotify's saved-tracks endpoint correctly, so heart toggles persist again across Spotify clients
- Clicking Favorites in the sidebar now loads the favorites list automatically again, and the first real favorites fetch replaces any optimistic placeholder entries instead of appending to them
- Navigation history is now tracked consistently across sidebar section switches, library detail selections, and pushed search destinations, with shared back/forward controls in the content toolbar
- Back/forward history restores no longer depend on a next-runloop reset flag; history recording is now suppressed until the exact restored snapshot is reached
- Search-result drill-down navigation now stores track IDs instead of full track payloads, so back/forward history does not retain large copies of search result arrays
- The navigation coordinator API no longer exposes ignored section/selection context parameters, and card/caller plumbing for those dead arguments has been removed
- Navigation history cleanup: removed the trivial back wrapper and documented why section switches clear the visible stack before history snapshots are recorded
