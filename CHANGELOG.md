# Changelog

All notable changes to Spotifly will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Changed
- A streaming grant waiting on the browser can now be abandoned. Closing the browser tab without authorizing sends nothing at all, so the enable affordance kept spinning with no way back to it — the row was disabled while waiting, so it could not even be pressed again. It stays enabled now and cancels instead of starting a second grant, in Speakers and on the login step alike. This is possible only because Swift owns the flow: librespot's listener had neither a timeout nor cancellation, which is why the previous version had to leave Skip enabled and hope. Cancelling is reported as its own outcome rather than as a failure, so abandoning a grant no longer shows an error the user caused deliberately
- The streaming grant now runs in Swift, and Rust is handed the token it produced. `spotifly_authorize_streaming` no longer opens a browser, reserves a port or exchanges a code — it takes an access token and does the part only librespot can do: connect once so the AP credentials land in the cache. The move is not a preference for Swift but a consequence of what the token is for. The same token that logs into the accesspoint also authorizes pathfinder and spclient, so it has to exist in Swift regardless, and a token minted in Rust was dropped on the floor immediately after the connect. It is adopted into `KeymasterSession` *before* the connect rather than after, so a grant whose librespot half fails still leaves the app holding a usable token. Gone with the flow: `librespot-oauth` as a dependency, the `STREAMING_SCOPES` list (Swift requests them now), and `pick_free_loopback_port` with its test — Swift's listener binds port 0 itself, which also closes the small race where the reserved port could be taken between releasing it and the listener binding it. The account-mismatch guard, the credentials cache and the supersession checks are untouched. One knock-on: the clippy `not_unsafe_ptr_arg_deref` baseline on the FFI surface goes from 8 back to 9, since this entry point takes a pointer again

### Added
- `SpclientAPI`, the REST half, starting with `metadata/4` track metadata. Same two credentials as the GraphQL client but plain REST, which makes it the more stable half to depend on: no query hashes to rotate, and entities come back whole rather than field-selected. Two details are mimicked from the real client rather than guessed at — a CORS preflight goes before the GET, since the endpoint is served to the web client's origin, and `market=from_token` resolves the catalogue against the account rather than the caller's IP. It also brings `SpotifyGID`, which converts the base62 ids the app uses into the hex form spclient addresses entities by; the conversion refuses an id too large for sixteen bytes rather than wrapping, since a silently truncated id would address a different track. The protobuf endpoints on this host — extended-metadata, storage-resolve — are deliberately left out until the Swift playback track needs them
- `PartnerAPI`, the pathfinder GraphQL client, with the four search operations `SearchService` needs — tracks, albums, artists and playlists. Nothing calls it yet; search still goes through the Web API until the migration task moves it. The API takes some explaining: `api-partner` accepts **persisted queries only**, so no query document is ever sent. The request is an operation name, its variables, and a SHA-256 hash naming a query Spotify holds — which means the field selection lives on their servers and cannot be changed here, and only the variables are ours. The hashes are vendored from libspot, and they rot: a new web-client release eventually retires them, so a `PersistedQueryNotFound` is surfaced by name rather than as a generic error, and the header comment records how to harvest fresh ones from the live web client if copying from libspot ever stops being enough. Two shapes needed bridging: search results identify albums, artists and playlists by URI alone with no `id`, while `AppStore` keys entities by id, so the id is derived once in `SpotifyURI`; and an unreadable item is dropped rather than failing the whole page, since one odd entry should not empty a search
- The `Client-Token` handshake, which is the second thing both partner APIs require alongside the bearer — a token identifies the *application*, so it is fetched unauthenticated and is independent of the keymaster grant. `clienttoken.spotify.com` speaks protobuf, so this brings a minimal writer and reader with it rather than a code-generation toolchain: the request is four scalars inside three nested messages, and the response needs two fields out of it. Field numbers come from `spotify.clienttoken.http.v0`, and the macOS platform submessage is sent empty, exactly as libspot does. The device id is stable across launches and stored in defaults rather than the keychain — it identifies the installation, not the user, and a fresh one each launch would look like a new device every time. Tokens are cached until they expire, concurrent callers share one fetch, and `invalidate()` exists for the 401 case where a token is dead before its stated expiry
- `KeymasterSession`, which holds the keymaster tokens and keeps them valid. An actor, because the token is about to be read from several places at once — the accesspoint session, pathfinder and spclient — and a refresh has to happen once rather than once per caller. Concurrent callers arriving during a refresh join the one already running, since two refreshes would each spend the same rotating token and the loser would then persist a replacement Spotify had already invalidated. The tokens are stored as one keychain item rather than a key per field, unlike the Web API half: the four values are only meaningful together, and a single write cannot leave an access token paired with another grant's expiry. Two subtleties are pinned by tests rather than by comments — the second refresh must spend the token the first one returned, and a refresh that omits the username must not blank the one the accesspoint needs, since only the initial exchange carries it
- A Swift implementation of the keymaster grant — `KeymasterAuth` plus a one-shot loopback listener — which is the first step of `plans/single-grant-partner-api.md`. Nothing calls it yet; the Rust grant still runs the flow. It exists in Swift because Swift is where the *token* has to end up: the same token that logs into the accesspoint also authorizes pathfinder GraphQL and spclient REST, and Rust currently mints it, hands it to librespot and drops it. `ASWebAuthenticationSession` cannot serve this flow at all, since Spotify's desktop client id is registered with a plain-HTTP loopback redirect rather than a custom scheme, so the browser opens normally and an `NWListener` on a system-assigned loopback port catches the redirect — one request, one reply, then it closes. The wait is bounded, because the other end of it is a person and a closed browser tab produces no request at all. The `state` parameter is checked before the code is read: anything on the machine can reach a loopback listener, and the state is the only thing tying a redirect to the request that started it. Two facts here were measured against the live service rather than assumed — the exchange needs no DPoP proof and no client token, and Spotify **rotates the refresh token on every refresh**, so the response's token replaces the stored one. Keeping the original would make the *second* refresh fail, roughly an hour in, presenting as a spontaneous logout rather than as an auth bug
- An "Enable playback" step, which is what actually restores local playback. It runs the streaming grant and appears in three places: as a step between logging in and the app, as an "Enable this Mac" row in Speakers, and as an alert when a play request has nowhere to go. The three exist because the state they describe is not "playback is off" but "this Mac is not a playback device" — and without a grant this Mac never registers with Spotify Connect, so it is genuinely missing from its own Speakers list. That absence is the indicator; the row is the way back. The alert appears only when nothing anywhere can serve the request, never while a remote device is playing. The login step is skippable and the skip is not remembered, since the prompt is worth re-offering and Speakers carries the same button either way. Existing users land on it once after upgrading, because their session predates the grant
- `SpotifyAPI.startPlayback`, which starts content on a remote device over the Web API. The player extension had transport controls only — pause, resume, next, previous, seek, volume, shuffle — so with no local Connect device a phone could be paused but an album could not be started on it. `resumePlayback` hits the same `/me/player/play` endpoint but sends no body, which resumes whatever is already loaded rather than starting something. The device goes in the query string, where Spotify reads it, not the body; an empty `uris` list is omitted rather than sent, since Spotify rejects an empty one and callers should not have to check first. Request construction is split into `makeStartPlaybackRequest` so the body and query can be tested without a network round-trip
- A one-time streaming authorization, `spotifly_authorize_streaming()`, which is what fills the credentials cache. It runs librespot's own OAuth flow with librespot's client id against a loopback redirect, then connects once so librespot persists the AP credentials. Two client ids are now in play and they are not interchangeable in either direction: `clienttoken.spotify.com` returns 400 for a dashboard client id, so it cannot obtain the client token login5 requires, and a token minted with librespot's id returns 429 from every Web API endpoint — both measured against the live service. The loopback port is chosen at runtime by binding port 0 rather than hardcoded, since Spotify accepts any loopback port for a first-party id and a fixed one would collide. There is no in-flight cancellation: the flow's own listener bounds it, and the UI's Cancel declines before it starts. Because librespot persists from inside `Session::connect`, a logout landing mid-connect is caught *after* the write rather than before it — the run then removes the credentials it just created instead of leaving them behind for the account that logged out

### Removed
- The reconnect loop no longer asks Swift for an access token. It opened a oneshot channel, fired a callback into Swift, waited up to ten seconds for a reply, and then re-checked the lifecycle generation *because* that round-trip is slow enough for a logout or a restart to land inside it. Every part of that existed to obtain a token minted with the user's dashboard client id — the one login5 now rejects — so an automatic reconnect would have failed at exactly the point the original outage did. A rebuild connects from the cached streaming credentials instead, and the channel, the ten-second timeout, the second generation check, `spotifly_register_token_request_callback`, `spotifly_set_token`, their C declarations and the Swift callback that answered them are all gone. One knock-on: the clippy `not_unsafe_ptr_arg_deref` baseline on the FFI surface drops from 9 to 8, since `spotifly_set_token` was one of them

### Fixed
- Logging out during the browser half of a streaming grant no longer leaves that account's credentials behind. The check itself is not new, but the ground moved under it: Rust used to hold the browser wait and snapshot the logout generation before it, so it could see a logout that landed during the wait. Swift runs the browser half now, so Rust's snapshot is taken *after* the logout and its own supersession check passes — the grant writes AP credentials and keymaster tokens for an account that is gone, and the caller's stale-run guard merely returned. That guard now undoes the run's own writes: it tears the session down and clears both halves of the grant, exactly as the wrong-account path already did
- A streaming grant authorized with a different Spotify account than the one signed in is now rejected instead of accepted. The second OAuth flow runs in the browser, with whatever account the browser is signed into — nothing tied it to the Web API session, so the app could browse, edit playlists and save tracks on one account while playing, queueing and controlling devices on another, with nothing on screen saying so. The grant now reports the account it authenticated as, and a mismatch clears the credentials it wrote and asks the user to sign the browser into the same account. Being unable to determine either side counts as agreement: refusing a grant because `/me` was briefly unreachable would be worse than the case being guarded against, which requires deliberately signing into a second account
- Four more defects in the streaming split, found by review before they reached anyone. A grant waits on a human in a browser, and `SESSION_GENERATION` advances on every rebuild rather than only on logout — so an ordinary play, retry or wake during that wait made the *successful* grant report itself superseded and delete the credentials it had just written; supersession now tracks a counter that only logout and app termination move. The device table was populated only by opening Speakers, and `activeDeviceId` derives from it, so the remote-playback path almost never triggered: a user who skipped the grant was told nothing could play while their phone was playing. Startup now keeps the device response it was already fetching for the premium check, and the play path refreshes once more before concluding that nothing can serve the request. Individual tracks were sent as `context_uri`, which Spotify rejects — `playTrack` and the queue both pass bare track URIs — so they now go in `uris`, with the offset dropped since it only means something inside a context. And Skip stays enabled while a grant waits, because the callback listener has no timeout and cannot be cancelled: closing the browser tab would otherwise strand a first-time user on that screen with no way in but relaunching
- Player initialization no longer hands librespot the Web API token, which is what kept playback broken and, worse, kept destroying the credentials that would have fixed it. `spotifly_init_player` had learned to accept a null token meaning "connect from the cached streaming credentials", but Swift still passed the dashboard-minted token, which `create_session` prefers over the cache — so login5 rejected it exactly as before. The compounding part: `Spirc::new` connects with `store_credentials = true`, so every one of those failed inits *wrote* its rejected credentials into the cache, overwriting the good ones a grant had just cached. The result was a loop where authorizing appeared to succeed and the next play attempt sent the user straight back to the browser. The token parameter is now gone from the whole initialization chain rather than passed as nil at the bottom, since a dead `accessToken` on an init function is what let this hide in the first place. A successful grant also builds the session immediately, so this Mac appears in Speakers instead of waiting for the next play

### Changed
- Logging out now also removes the cached streaming credentials. They are a file in the app container rather than a keychain item, so clearing the keychain does not touch them — and left behind, they would let the next launch connect the account that just logged out, which is the same class of bug as the Spirc connection that used to survive a logout. Removed after the session teardown, so no live session can write them back on the way down
- Playing something with no local Connect device now starts it on the active remote device instead of failing. `play` and `playTracks` both opened with a `guard isInitialized else { errorMessage = "Player not initialized" }`, so when this Mac was not a playback device every play attempt was a dead end — even with a phone or a speaker active and perfectly able to serve it. The decision is now an explicit `playbackTarget`: local when the local player exists, the active device over the Web API when it does not, and only when there is neither does the user get asked to authorize streaming. That last case is the sole one that prompts — pressing play while a remote device is playing must not nag about local streaming. A remote start also resyncs afterwards, because with no Spirc session there are no playback or queue callbacks and the now-playing bar would otherwise keep showing whatever it showed before; the resync captures `liveStateRevision` before it awaits and skips the write if a logout moved it, since a superseded run must not write. `PlaybackViewModel` reaches `QueueService` through a reference injected at startup, mirroring how it already receives `AppStore`, rather than threading the service through six call sites in the views
- The librespot session connects from credentials cached on disk instead of from an access token. Spotify changed a server-side rule around 2026-08-11: login5 now rejects stored credentials that descend from a token minted with any client id other than its own desktop one, and Spotifly mints its token with the user's own dashboard client id. The AP still authenticates, so the failure lands one step later, at `Spirc::new` — `FaultyRequest(INVALID_CREDENTIALS)` — and takes local playback down completely while browsing continues unaffected. `Cache` is given a real credentials directory, which it never had, so `Session::connect` persists what the AP hands back and every later init connects from that with no token, no refresh and no round-trip beforehand. `create_session` resolves the credential itself — a freshly granted token when there is one, the cache otherwise — so callers do not each repeat the rule, and `spotifly_init_player` now accepts a null token meaning exactly that. Nothing yet writes to the cache; the grant that fills it comes next

## [1.2.6] - 2026-08-12

### Changed
- `currentPositionMs` is derived instead of stored. Once `anchorPosition` owned the write, the field was assigned on every update to exactly `min(positionAnchorMs, trackDurationMs)` — a cache of a one-line derivation, whose only possible disagreement with its source was being stale. It is now computed from the anchor, so the view model holds one position instead of two that had to be kept in step, and the clamp both it and `interpolatedPositionMs` apply lives in a single `clampedToTrack` helper. One behaviour improves as a side effect: a duration arriving *after* a position now caps it, where the stored copy kept whatever value it was written with
- The once-a-second drift check is a `Task` instead of a thread and a notification. It ran on a manually managed `Thread` looping on `Thread.sleep`, which posted a `NotificationCenter` notification, observed on the main queue, which hopped to the main actor to call one method — about forty lines and a process-wide notification name to schedule a single timer. Its comment cited avoiding "Swift concurrency issues", which predates the project's settled `@MainActor` isolation; the view model is main-actor-isolated, so an awaiting `Task` sits on the right actor with no hop and no observer. Two loose ends went with it: the timer's `stop()` was never called and the observer was never removed, both harmless only because the view model is an immortal singleton, and the replacement is cancellable and holds `self` weakly
- Position anchoring goes through one method instead of eleven copies. `positionAnchorMs`, `positionAnchorTime` and `currentPositionMs` describe one fact between them — where playback is, and when it was there — but were assigned separately at every site that moved the playhead: initialization, next, previous, seek, resume, the disconnect freeze, the loading notification, the Mercury and Web API state handlers, the Rust anchor sync, and the drift correction. They had already come apart: two of those sites clamped `currentPositionMs` to the track length and eight did not, with nothing recording why. `anchorPosition(_:at:)` now owns the write and the clamp, so the frozen value agrees with the interpolated one, which clamps too; an unknown duration clamps nothing, which is what keeps a track change safe, since the URI `didSet` zeroes the duration before the new position arrives. The optional `at:` carries the one real variation — a Mercury or Web API snapshot that was true earlier and anchors its clock back by the elapsed time rather than restarting it
- Connection-state snapshots now carry a monotonic revision assigned by Rust, and Swift drops any that arrives after a newer one. Three Rust tasks publish independently — the event listener, the cluster listener, the reconnect loop — and the hop to the main actor gives no ordering guarantee between them, so a delayed callback could deliver an older snapshot last and leave subscribers acting on a readiness that was no longer true. The revision is assigned while the state is read, under its own lock, so it orders snapshots by what they actually saw; delivery stays outside that lock, because handing the payload to Swift re-enters the callback and must never happen while holding one. The synchronous `getConnectionState()` pull is published the same way, since Rust stamps it too — otherwise a callback already queued behind that call would overwrite what was just read, and merely suppressing that callback would leave the subject holding the older value. Two alternatives were rejected: re-reading the current state on arrival also fixes the ordering but erases readiness *edges*, and the recovery re-sync in `LoggedInLifecycleModifier` triggers on exactly that `false → true` transition; a serial dispatch queue is banned by the project's Swift guidelines and would not have ordered the snapshots anyway, since decoding happens before the hop
- Playback transfers are serialized instead of running concurrently. Each speaker row launches its own task, and `transferPlayback` optimistically marks its target active and undoes that when Rust rejects the transfer — sound only while nothing else is in flight, since overlapping attempts capture each other's optimistic values as the state to restore, and two rejected transfers could leave a device marked active that never became active. Attempts now chain onto the previous one, so the later tap still wins because it runs last. A rollback additionally only fires when no authoritative active-device update arrived from the cluster while the transfer was awaited — another client activating a device mid-transfer outranks restoring what was true before the tap, including when it names the very device that was asked for, which the store alone cannot tell apart from the optimistic update
- Logging out during a network outage now actually stops playback. `PlaybackViewModel.stop()` was gated on the session being connected, borrowed from the transport commands — those go through Spirc, which rejects them without a session, so acting on them locally would desync the UI. `spotifly_stop` is not one of them: it stops the Player directly, a local teardown that works while disconnected. The guard meant logout returned early during an outage, leaving buffered audio playing and the previous track still showing
- The queue refresh scheduled after a provisional `SetQueue` now retries instead of giving up silently. librespot emits a `SetQueue` carrying a context but no tracks while it is still filling one in; Swift keeps the existing queue and schedules a Web API refresh to recover the real one. That refresh was one-shot, and the freshness barrier discards the whole bootstrap response whenever a Rust callback lands mid-fetch — which is likely in exactly this window, since starting a context produces cluster updates. The safety net therefore failed silently and left "up next" stale until the next real `SetQueue`. `fetchInitialPlaybackState` now reports whether it applied anything, and the refresh re-attempts up to three times. The queue contents are not a usable signal here: a provisional `SetQueue` preserves the previous queue, so a discarded response and an applied one can look identical. Splitting the freshness counter into separate playback and queue halves was tried first and reverted — both halves carry the current track, so per-half checks let a stale queue response reinstate a track that a live playback callback had already moved past
- The Web API bootstrap no longer runs twice on every launch. The reconnect handler treated any rise to ready as a reconnect and re-fetched playback state, guarded only by `wasConnectionReady` still being nil — which never held, because `connectionState` is a `CurrentValueSubject` and delivers its seed the moment the view subscribes, so the first real transition was never the first callback. The startup task fetches the same thing moments later. A reconnect is now recognised as what it actually is: a drop followed by a rise
- Logging out now tears the librespot session down instead of only clearing the token. `AuthViewModel.logout()` cleared Keychain and memory and left Rust untouched, so the Spirc connection stayed registered on Spotify Connect for the account that had just logged out — and with no shutdown flag set, the recovery loop treated the next network hiccup as an outage worth fixing and re-announced the device. A confirming log showed exactly that: 30 seconds after logging out mid-outage, `active device is <spotifly_…>`. Logout now says goodbye and then releases Session, Player, Mixer and Spirc, which also invalidates the session generation. Several orderings had to be closed around it: the teardown is awaited before the auth state is cleared, so no login can start a rebuild while one is going down; `spotifly_shutdown` publishes the disconnected snapshot itself rather than waiting for the listeners, since a snapshot still claiming a ready Spirc is what let Swift adopt the dead session as healthy; an initialization overlapping a logout is neither cancelled (`waitUntilReady` swallows cancellation and would spin on the main actor) nor waited for (a stalled setup would hang the logout) but invalidated by a lifecycle generation, checked on both the success and the failure path because the superseded attempt reports failure while leaving a live session behind; a rebuild finishing during a teardown clears what it built, shutting down through its own Spirc handle because a cleanup may already have nilled the global one; and no initialization may start while a logout runs
- Removed a duplicate `stop()` on logout. `LoggedInView` passes `handleLogout` as `onLogout`, which already stops playback, and the profile view's own closure called `stop()` again before invoking it — visible in the logs as `spotifly_stop called` twice, two milliseconds apart. Idempotent, so harmless, but the second call was pure noise
- Fixed a deadlock that could hang the app during a reconnect. `AudioRenderer.stop()` stops the consumer but never signalled the semaphore a blocked writer waits on, so if the ring buffer happened to be full at that moment, `writeAudioData` looped on 500 ms timeouts waiting for space nothing would ever free. The caller is librespot's player thread, so the teardown froze at `Shutting down player thread` and never completed. Latent before, but reachable on every reconnect since the audio-throttle fix started sending a stop when the Player is torn down — *before* it is dropped, while it may still be writing. `stop()` now wakes the writer, and the writer gives up instead of waiting when the renderer is no longer rendering, dropping audio destined for a renderer that has stopped
- The playback position no longer runs ahead while the connection is down. Two clocks were extrapolating: Swift interpolated from an anchor, and `spotifly_get_position_ms()` separately added wall time since the last Player event, capped at exactly 5000 ms. When a reconnect tore the Player down, `POSITION_MS` froze but `IS_PLAYING` stayed true, so Rust kept returning `last + 5000` — while rehydration correctly resumed from the raw value, surfacing the gap as a five-second backwards snap. Rust now reports only what the Player last said (it emits updates every 200 ms, so the removed extrapolation added no smoothness), and Swift is the sole display interpolator, advancing only while the connection is ready and freezing at the real position when it drops. The once-a-second drift check also compares even when Rust's value did not change — a frozen value is exactly when the old "only if it changed" guard suppressed the correction that was needed. Two latent bugs fell out along the way: the drift computation could trap on `Int32` overflow, and the position was clamped to zero whenever the track duration was not yet known
- Swift now adopts a recovery that Rust completed on its own. If an explicit initialization failed after the Rust session had been created, `isInitialized` stayed `false` — and when the health check or reconnect loop later rebuilt Rust successfully, nothing told Swift. The next play would call `initializeIfNeeded`, whose `SpotifyPlayer.initialize` starts with a `cleanup()`, tearing down the session that had just been restored. `PlaybackViewModel` now watches the connection snapshot and marks itself initialized (clearing the stale error) when Rust reports connected and Spirc-ready while no explicit initialization is in flight. It deliberately does **not** clear the flag on a not-ready snapshot: transient disconnects belong to Rust, and dropping the flag there would send the next user command straight back into a destructive Swift rebuild
- Removed the Swift reconnect watchdog, which could permanently disable Rust's recovery. After 120 seconds without a ready connection it ran a destructive cleanup-then-init: the cleanup invalidates the generation, so any reconnect loop working the problem abandoned, and if the single init attempt then failed because the network was still down, nothing was left retrying — no loop, and no new watchdog either, because arming one requires a ready-to-not-ready transition and the state was already not-ready. The session health check did not rescue it: it triggered on `Session::is_invalid()`, a flag only set by `shutdown()`, so a session created by a failed init reports itself valid forever. Recovery now belongs to Rust alone, which retries unbounded. Two supporting fixes: the health check now triggers on "not connected and nobody is recovering" rather than only on invalidity, which also closes the same trap at startup when the very first initialization fails; and system wake asks Rust to reconnect instead of rebuilding from Swift, falling back to a full rebuild only when there is no session to reconnect to (after a logout, or when initialization never succeeded). Also drops a latent inconsistency — the watchdog armed on `sessionConnected && spircReady` but its timeout only re-checked `sessionConnected`
- Simplified the code this branch had grown over ~20 incremental commits, with no behavior change: **949 lines removed, 503 added**. In Rust, two helpers replace a callback-invocation dance repeated 13 times (`registered_callback` copies the pointer out and drops the slot lock before returning — a callback must never run holding it, since it re-enters Swift; `send_json` folds serialize-and-hand-over), a `spirc_command` helper collapses six near-identical command wrappers, `c_string_arg` folds the null-and-UTF-8 check at seven FFI entry points, and the two mirror-image queue loops become one `collect_queue_items`. Comments left stale by the soft-reconnect removal were rewritten rather than deleted, and `create_new_player` no longer returns a `Result` it could never fail with. In Swift, `decodeJSONObject` absorbs the nil/UTF-8/parse preamble repeated across six JSON callbacks, and `sendTransportCommand` replaces the active-device-versus-remote branch duplicated across six transport methods — returning `Bool` so the optimistic UI updates that follow still run only when the command was actually issued. Deliberately untouched: the publish-once ordering in `init_player_async`, the generation predicates, every main-actor hop in the bridge callbacks, and `AudioRenderer.start()`'s re-anchor path. The crate now also compiles warning-free
- Replaced soft reconnect with a single recovery strategy: tear everything down and rebuild Session, Player, Mixer and Spirc as one generation, then restore the captured intent (re-activate if Spotifly was the active device, auto-resume if it was playing). Soft reconnect kept the Player alive across sessions to avoid an audible gap, but a Player outliving the Session it was built for is what forced most of the surrounding complexity: the librespot patch making Spirc adopt an orphaned `play_request_id`, a context reload after every reconnect (with its seek-to-position blip), and a watchdog that re-issued play commands when the audio key fetch on the dead session silently timed out. A brief gap during a network outage is the better trade. This removes `soft_reconnect_async`, `do_soft_reconnect_cleanup`, the `Player::set_session` path, the pending-play watchdog and the whole `PendingPlay` bookkeeping that existed only to feed it — **194 lines deleted, 11 added**. The rebuild path is not new code: it was already the fallback whenever soft reconnect failed
- Extracted the reconnect and active-device decisions in the Rust layer into pure functions (`should_recover_after_deactivation`, `should_recover_after_cluster_end`, `is_active_in_cluster`, `teardown_in_progress`) and added the first unit tests the crate has ever had. The rules that decide whether a disconnect is a real outage or an ordinary Connect handoff were previously inline conditions inside a 3000-line event loop, reachable only by running the app against a live Spotify session — so the distinction that caused the reconnect-on-handoff bug could not be verified at all. Eight tests now cover it, including that deactivation alone does not reconnect, that a dead session does, that sleep and shutdown always suppress recovery, that only the current session generation's cluster listener may act, and that an empty active-device ID clears activity. Run with `cargo test` in `rust/`
- Consolidated the Rust connection snapshot behind a single lock. `session_connected`, `session_connection_id`, `spirc_ready`, `device_id`, `reconnect_attempt`, `last_error`, and `connected_since_ms` previously lived in six independent globals (three mutexes and three atomics), and `build_connection_state_info` assembled a snapshot by locking them one at a time — so a published snapshot could mix values from different transitions (ready from one, connection metadata from another). They now live in one `Mutex<ConnectionState>` reached through a `with_connection` helper, which makes every snapshot internally consistent by construction and removes five globals
- Unified the Swift-side connection-state decoding. The payload was parsed twice with duplicated permissive dictionary code — once in the push callback, once in `getConnectionState()` — where a renamed or missing field silently became `false`, `0`, or `""` and was indistinguishable from a genuinely disconnected session. Both paths now share one `Decodable` decode with required fields non-optional, so schema drift is logged as a decode failure instead of manufacturing plausible state. `LibrespotConnectionState` is declared `nonisolated` at the type level (not just per-property) because the project builds with `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor`, which would otherwise give it a main-actor-isolated conformance the C callbacks can't use — this is what the previous hand-rolled parsing was working around

### Fixed
- Logging out drops what was playing, so the next account cannot resume it. `spotifly_cleanup` reset the whole playback lifecycle — playing, position, resume point, shuffle, repeat, volume, active device — but left `CURRENT_TRACK_URI` and `CURRENT_CONTEXT_URI` behind, and those two are exactly what `resume_via_load` loads: the context, with the track as its hint. Nothing after a login rewrites them until playback establishes something new, because `update_current_context_uri` ignores empty values and the track URI is only ever written from player events. So pressing play as a freshly logged-in account reached an activated Spirc with no queue, `play()` produced no `Playing` event, and the fallback loaded the previous account's context — reachable through the ordinary control path, where `sendTransportCommand` takes the Web API's no-active-device 404 and falls back to `spotifly_resume`. The same hole in `RESUME_POSITION_MS` was closed one commit earlier, which is what left this as the position's target with no position. Only the full cleanup clears them: the wake and reconnect paths run `do_reconnect_cleanup`, which deliberately leaves playback state alone so the rehydrating load has something to reload. Logout and an explicit rebuild are the cases where Rust genuinely has no track or context loaded afterwards — which Swift already assumed, since `performInitialization` nils its own `currentTrackUri` for that reason
- A stale cluster timestamp no longer parks the progress bar at the end of the track. Both paths that anchor a position from a timestamped snapshot back-date the clock by the elapsed time, so interpolation reports the current position rather than the measured one — correct and necessary while monitoring a remote device, where `position_as_of_timestamp` plus elapsed genuinely is where that device is now. The Web API path discarded that compensation when it would carry the position past the end of the track; the Mercury path did the same arithmetic with no such bound, so a sufficiently old cluster update anchored the clock minutes in the past and the bar sat pinned at the track end while the remote device played on. Staleness is a property of Spotify's timestamp, not of the endpoint that delivered it: cluster updates forward `player_state.timestamp` unchanged and it can be minutes old, while local callbacks stamp the current time and compensate by nothing. Both paths now share one `positionAnchor(forPosition:takenAt:)`, which also removes the duplicated arithmetic. Clamping the compensation to land exactly on the track end was considered and rejected — `clampedToTrack` already bounds the display, so it looks identical to no guard at all, tidying the arithmetic without changing what the user sees; discarding shows a genuinely measured position that is merely behind and that the next update corrects. The bound reads `trackDurationMs`, so it is by construction the same length the display clamps against
- Resuming after the device stopped being active continues the track instead of restarting it. `resume_via_load` seeks to `POSITION_MS`, and `PlayerEvent::Stopped` zeroed that — while librespot sends `Stop` to the Player on every deactivation, from `handle_disconnect`. The resume point was therefore destroyed at deactivation, potentially minutes before anything asked to resume, and playback came back from 0:00. One global was serving two meanings that disagree here: where the Player is now, for which zero is right once it has stopped, and where playback should pick up, which has to survive a stop. `Stopped` still resets the live position, because that event cannot say why playback stopped — `handle_stop` runs for a deactivation, for a queue that has run out, and for `prev` at the first track, and keeping the position for all of them would make `next` on the last track leave a resume point mid-track, so pressing play afterwards restarted it there instead of from the beginning. The resume point is instead captured where the cause is known: the `SessionDisconnected` arm, which librespot emits from `handle_disconnect` just before the `handle_stop` that follows it. It is cleared once playback is running again and consumed by the resume path, so it can never outlive the deactivation it belongs to. This removes a wart rather than adding one — `freezePositionForDisconnect` already carried a workaround for Rust reporting zero after a teardown, and two other readers improve as well: the drift check's playing-state sync now lands on where playback really stopped, and the position published alongside shuffle/repeat changes no longer clobbers Swift's anchor with a zero, which is what overwrote a correct 12087 ms in the confirming log
- The French tooltip on the scroll-to-current-track toolbar button said "Ouvrir la file d'attente" ("Open the queue"), a copy of the `queue.open` translation four lines above it in `fr.lproj/Localizable.strings`. It now reads "Aller au titre en cours". The rest of the French `queue.*` group matches English
- Only one resume runs at a time. `Spirc::play` only queues a command, and `spotifly_resume` waits half a second for a `Playing` event before falling back to loading the saved context and waiting two more — while Swift dispatches each press to its own detached task. Pressing play repeatedly, which is precisely what an unresponsive play button provokes, therefore stacked several play-then-load sequences, each capturing the position at its own moment and restarting the track there. `IS_PLAYING` did not cover the gap, since it stays false until the first sequence produces audio. A resume already in flight now reports success to later callers instead of starting a second one, which also closes the same race on the path where Spotifly is already the active device
- The Now Playing bar's queue counter no longer reads one past the end. `currentIndex` is `previousTracks.count`, which sits one beyond the last item whenever the queue holds history but no current track — a state a queue reaches simply by playing out, and the state the sleep-wake queue wipe left behind — so the label rendered `9/8`. The index is honest; the sentence was not, because "track n of m" needs an n. The counter is now shown only while a current track exists; the button keeps its slot and shows the queue glyph instead, since the counter was its only label and dropping it outright would have left an invisible control that VoiceOver announces unnamed. It also gained a tooltip and an accessibility label, which it never had. `QueueListView` needed no change: it uses the same index for the played/pending split, where treating every entry as played is correct when none is current, and its scroll-to-current already guarded the bound
- Transport controls work again when no device is active anywhere — most visibly, the play button after waking from sleep, which could not resume a paused track at all. `sendTransportCommand` routed on `isActiveDevice`, a two-valued flag standing in for a three-valued fact: Spotifly is the active device, another device is, or nobody is. It read the third case as the second and sent the command to a Web API with no device to deliver it to; Spotify answered 404, `throwAPIError` flattened that into a generic `apiError`, and it landed in an `errorMessage` nothing displays — so each press produced one request and no playback. Sleep reaches that state through Spotifly's own teardown: `spotifly_disconnect` shuts Spirc down, librespot answers any shutdown with `SessionDisconnected`, and its handler clears the active flag, so the wake path captures `was_active: false` and rebuilds passively. 404 from the player endpoints is now its own `noActiveDevice` error, and a transport command that hits it falls back to the local player, which takes the Connect role on the way through: `spotifly_resume` activates and then reloads the saved context at the saved position. Activating first is a precondition rather than a nicety — `SpircTask` matches `_ if !self.connect_state.is_active()` ahead of every transport command, so `Play`, `Load`, `Next`, `Prev`, `Shuffle` and `SetPosition` are discarded with a warning while inactive, and the resume path including its load fallback would have been dropped in silence. The same catch-all exposed a latent trap in `resume_via_load`, which recorded the device as active whenever `Spirc::load` returned `Ok` — but `Ok` only means the command reached the channel, so a discarded load looked like a successful takeover and left Swift routing every later command to a local player that was ignoring all of them. Activity is now recorded only where it is actually established, never inferred from a queued command. What this recovers is resume, which is also the only one that needed recovering: with nobody active there is no context loaded and no track playing, so pause, next, previous, seek and shuffle reach an inactive Spirc and are correctly dropped — there is nothing to pause or skip. Activating for those would take the Connect role from the user's other clients to accomplish nothing, and making them work would mean silently starting playback in response to "next" or "seek". Two alternatives were rejected: re-activating unconditionally on wake fixes only the sleep path and would take the Connect role back from a phone that legitimately took over while the Mac slept, and publishing the cluster's active-device id in the connection snapshot adds a second piece of cluster state to keep accurate across every rebuild — `LAST_ACTIVE_DEVICE_ID` shows the trap, since it is a notification latch that is never cleared on reconnect and afterwards holds a stale *own* device id that would read as "a remote device is active"
- Waking from sleep no longer empties the queue. The reconnect that follows a wake re-bootstraps from the Web API, and with no device active Spotify answers both `/me/player` and `/me/player/queue` with 204 — which decodes to a nil playback state and an empty queue, indistinguishable from a genuinely empty one. That is the absence of an answer, not an answer that nothing is queued, and applying it was worse than it looked: `setQueue`'s `previous: nil` contract preserves the history and overwrites the rest, so the pending tracks — the one part no later callback reconstructs — were destroyed, together with the current pointer, which `Queue.reconciled` then could not repair because it can only re-split a list that still contains the track. The result was a Queue section showing only played tracks while the Now Playing bar still showed the paused track, since the bar is fed by a response that was nil and therefore never applied. A bootstrap response carrying no playback state, no currently-playing track and no queued tracks is now recognised as carrying nothing and leaves the queue untouched
- Navigation now has one route value and one back/forward history across sidebar sections, library selections, search results, and stack drill-downs. Native stack pops share the toolbar's Back semantics; every user navigation is replayable; deleted entities and evicted bounded search queries are invalidated across the whole history; and clearing the search field preserves its cached, query-keyed result route
- The queue's current pointer now follows the logical track that is actually playing instead of the stale split from librespot's initial `SetQueue`. Spotifly preserves the reported ordering, finds the nearest matching occurrence in either direction, and re-splits whenever either playback URI or queue data arrives; starting deep in an album, automatic transitions, next, and previous therefore keep the position indicator, played-track dimming, remaining count, and scroll target aligned without a Web API refresh
- Web API track relinking now preserves the originally requested track as Spotifly's identity. `linked_from` supplies the stored ID and URI while the playable replacement still supplies its metadata; field-projected responses request that reference explicitly, supported endpoints request the user's market, and playback bootstrap data follows the same identity rule. Playlist/search results, queue hydration, Now Playing, favorites, and playlist writes therefore agree on one logical track instead of caching or sending Spotify's market-specific alternative ID
- The app no longer runs two `AppStore` instances. SwiftUI calls a View's `init` repeatedly but keeps only the first `State(initialValue:)`, and `LoggedInView.init` did two things that outlived that discard: the services subscribed to the global player subjects inside their own initialisers, and `setStore` mutated the shared `PlaybackViewModel`. The discarded `QueueService` therefore kept handling every Spirc notification against its own empty store — re-fetching all queue metadata on each one — while the shared view model ended up reading that discarded store, so the macOS Now Playing panel and the in-app bar resolved against different data. `QueueService`, `ConnectionService` and `DeviceService` now construct inert and are started by an idempotent `activate()` from the surviving view's lifecycle task, alongside `setStore`, so construction has no observable effect however often it runs
- Track metadata is fetched in one request instead of one per track. `SpotifyAPI.fetchTracks` fanned out to a `/v1/tracks/{id}` GET per ID through a task group, so hydrating an 18-track album queue issued 18 requests — the batch endpoint `/v1/tracks?ids=` takes 50 at a time. The 50-ID chunking moved down into the API layer, where that limit comes from; `TrackService` no longer splits IDs it has no reason to know the cap for. Spotify answers positionally with `null` in the slot of an ID it has no track for, which the response is zipped back onto, so an unavailable track cannot shift the tracks after it onto the wrong IDs
- A logical current track that is not yet in `AppStore` now recovers its title, artist, artwork, and duration without waiting for another queue callback. Queue hydration and Now Playing recovery share one per-track in-flight registry in `TrackService`, so overlapping batches do not duplicate requests; cache hits avoid token work, caller cancellation does not cancel useful shared loading, and failed requests can be retried. A track Spotify answers without — one that does not resolve for the user's market — is remembered as absent rather than re-requested on every queue update, while a request that failed outright still retries
- Relinked Spotify tracks now keep their logical context identity throughout playback instead of replacing it with librespot's playable-alternative ID. The in-app and macOS Now Playing surfaces therefore resolve the same normalized track metadata, favorite state, artwork, resume hint, and radio position while still using the decoded audio item's authoritative duration. Track changes also clear the previous stream duration and stale system metadata before adopting the new track, preventing a previous title or cover from being paired with the next track's timing
- Albums that opened with a header and no tracks now load. Every album, artist and playlist detail fetch ran *inside* the view's `.task`, so SwiftUI cancelling that task on teardown cancelled the request — and the resulting `URLError.cancelled` was rendered as the album's error, the red `Abgebrochen` under the play button. Teardown was routine: the detail router picked between an `init(album:)` and an `init(albumId:)` depending on whether the entity was in the store yet, and those are the two branches of a `_ConditionalContent`, with structural identities that `.id()` does not unify, so the moment another producer inserted the entity SwiftUI destroyed the view that was fetching it. A second caller that arrived meanwhile fared worse: `AlbumService` waited for the first by polling a flag every 50 ms, read the flag's disappearance as success, and returned an empty track list with no error and no retry, so the album stayed blank until you navigated away and back. Fetches now run in an unstructured task owned by the service (`InFlightRequests`), which a cancelled caller does not take down with it; the result lands in `AppStore` and the view that replaced the cancelled one reads it there. Detail views read the store rather than keeping their own `@State` copy, so there is one branch and one initialiser, and a cancellation is no longer shown as a failure
- Every section fetches each thing once. `AlbumService.fetchAlbumDetails` had no in-flight deduplication at all and two entry points into it (`loadAlbum` then `loadTracks`), `ArtistService` had none of any kind, and `PlaylistService` had a per-ID task map that only covered one of its paths — three sections, three different answers. All of them now go through one keyed single-flight registry, as do the four library list loads, which were four hand-written copies of the same stored-task dance
- Opening an album no longer re-fetches metadata the app already has. `/albums/{id}` was requested beside `/albums/{id}/tracks` even when the album had just come from the library list, an artist page or a search result; the same for playlists. Albums carry an explicit `detailsLoaded` marker now — presence alone is not enough, since `TopItemsService` synthesises a stub from a track's album object — and only the missing half is requested. An artist's discography is cached in the store instead of living in the view's `@State`, where it was re-fetched on every visit, and the detail views ask `/me/tracks/contains` only about tracks whose status is not already known
- An album or playlist that genuinely has no tracks is no longer re-fetched forever. `tracksLoaded` was defined as `!trackIds.isEmpty`, so "loaded and empty" was indistinguishable from "never loaded" — including for a playlist the user had just emptied. It is now set by the load, whatever came back
- A failed reorder actually rolls back. The rollback re-read the playlist "from the server" through a cache-respecting call, which saw a loaded playlist and returned the optimistically reordered list it was supposed to undo, without issuing a request. It now re-fetches the tracks, and says so when even that fails
- A track or album list that fails to load can be retried. The retry button lived in a branch only reachable while the entity itself was missing — which it usually is not, since the list you clicked from put it in the store — so a failed track list showed bare red text, and a failed artist discography showed nothing at all
- Nothing is asked for twice, and nothing is asked for that is already known. An album opened from a search result re-fetched metadata the search had already returned, because `SpotifyAPI+Search` builds its albums with the memberwise initialiser and so inherited the "details not loaded" default; `detailsLoaded` has no default any more, so a producer has to say what it knows. Two views wanting the same track's favorite status in one frame both asked, since the resolved-status cache is only written when a check returns — they now join one cancellation-resilient in-flight request, so replacement views cannot miss the result either. Returning to a search re-asked about the same tracks, because search, the search track list and the queue used the deliberately cache-ignoring `refreshFavoriteStatuses`; only the now-playing bar keeps it, as the single place where a track favorited in another Spotify client can still surface. And the loading paths no longer fetch an access token before deciding whether they need one: the services hold a token provider, as QueueService already did, so a cache hit touches the session not at all — opening one album used to log sixteen token fetches that led to no request whatsoever
- A pull-to-refresh no longer races the load it replaced. Cancellation is cooperative, so a superseded run whose response had already arrived went on to write its page over the refresh's reset and to clear the loading state the replacement had just set. Superseded runs now check before writing. In the same family: a reorder whose reconciliation was cancelled by a newer reorder was read as a failed reorder, and rolled back over the newer one

- A reconnect no longer reports success before playback is actually back. `Spirc::load()` only queues a command, so the rehydrating load could be accepted and then never take effect, leaving a session that reads ready but plays nothing — and Swift's Web API bootstrap could land in the gap between the load and playback resuming. The result is now acted on rather than logged: a closed command channel fails the attempt so the loop builds a fresh session, while absent resume metadata (reachable when an outage lands between a play command and the events that record what is playing) is not treated as a failure, since that would make every later attempt fail identically forever. On success the rehydration waits up to three seconds for the Player to actually start before readiness is announced. Connection success — ready flags, connected-since, backoff reset — is now committed once at the very end rather than when Spirc is created, so no intermediate snapshot can announce a session that cannot yet play and a failure leaves the previous disconnected state untouched. The commit is skipped if the initialization was superseded or a teardown started while it waited
- Whether an outage resumes playback no longer depends on event ordering. The reconnect task read `IS_PLAYING` and the active-device flag when it *started*, but between the disconnect and that moment the deactivation handler clears the active flag, a `Stopped` event clears playing, and a final cluster update can clear both — so a real outage could come back silent and passive purely because the events arrived in an unlucky order. The intent is now captured at each of the five recovery triggers, before anything clears it, and passed explicitly into the loop as a `RecoveryIntent`
- A superseded listener can no longer overwrite current state. Both long-lived Rust listeners now check their generation before processing anything: the player event listener only guarded its `SessionDisconnected` arm, so every other event — position, playing, track change, active device — still applied; the cluster listener checked only *after* its stream ended, leaving every message before that unguarded. Replaced listeners drain asynchronously after their successor is live (the logs show them delivering seconds later), so both could write state belonging to a session that no longer existed. The guard skips only when an event is actually present, so a closed channel still reaches the shutdown path instead of spinning
- The playback position no longer jumps to a stale value and back after a reconnect. Readiness was published the moment Spirc existed, while activation and the rehydrating load still had to run. Swift reacts to that publication by bootstrapping from the Web API, so it fetched and applied a server snapshot — in one measured case 145010 ms with a timestamp 144 seconds old — which Rust then overwrote 300 ms later with the real position of 99240 ms. `init_player_async` now builds a complete session and publishes its readiness exactly once, at the end: Spirc created, device activated, playback rehydrated, *then* announced. The activation path records its state without publishing (`store_active_device`) for the same reason, since publishing between activation and rehydration would reopen the same window. Chosen over the alternative of having Swift skip the Web API when playing locally, because that keys off state which is still settling at that moment — activation lands 483 ms after the bootstrap fires — and it would still have gone wrong for a track that was paused when the outage hit
- Playback no longer races after a reconnect. `AudioRenderer` paces the decoder by comparing audio written against wall clock since an anchor, because `AVSampleBufferAudioRenderer` accepts data eagerly and provides no real-time back-pressure. That anchor is reset in `start()` — but `start()` returns early when it is already rendering, and dropping the `Player` during a rebuild never ran `Sink::stop`, so the renderer kept believing it was rendering and the anchor survived the whole outage. On resume the throttle saw a large accumulated deficit, never slept, and let the decoder run flat out: measured at ~40 seconds of audio in under one second. Playback still *sounded* continuous because the renderer plays its buffer out in real time, but `EndOfTrack` fired ~40 s early and Spirc advanced the track with the audio still playing. Fixed on both sides — Rust now sends a stop when tearing a player down, and `start()` re-anchors the throttle even when it returns early (only the anchor, since a full pipeline reset mid-playback would glitch the audio)
- A dead session is now noticed even when Spotifly isn't the active device. Every existing recovery trigger needs something to happen: the cluster listener only acts when its stream *closes*, and librespot's dealer retries internally so that stream can stay open for minutes past a dead session; the zombie check in `require_session_connected` only runs when a command is issued. While Spotifly is playing, something trips one of those within seconds. While playback is on another device, nothing does — no commands are issued, so nothing calls `mark_disconnected`, so the published snapshot still reads "connected" and the Swift reconnect watchdog never arms either. Observed in testing: after a real outage with playback on a phone, the session stayed silently dead for 1m43s and only recovered because the machine happened to sleep and wake. A periodic check now polls `Session::is_invalid()` once a minute and starts the normal recovery when it finds a dead session. It costs one sleeping task per session generation waking once a minute to read two booleans, and exits when its generation is superseded, so it dies with the session it belongs to
- Playback now actually resumes after a reconnect. The rebuilt Player has no track loaded, and nothing else loads one — Spirc coming up ready and the device becoming active again only makes it *available* to play. So the session returned healthy and completely silent, while the UI kept showing the pre-outage track and position because `IS_PLAYING` and the position anchor survive the rebuild. The recovery path now issues one deterministic load of the captured context, seeking to the captured position, when playback was local and running before the outage. This replaces a five-second "auto-resume" window that waited for a `Paused` event on the assumption that the track would load itself via `transfer(None)` — nothing in that path ever called `transfer(None)`, so the event never arrived and the window did nothing. It went unnoticed because the rebuild was previously only the fallback for a failed soft reconnect, which kept the Player playing on its own
- Automatic recovery from a network outage now actually retries. Two bugs, both found by unplugging ethernet mid-playback. First, the reconnect loop invalidated itself: each attempt calls `init_player_async`, which bumps the session generation *before* it can fail, so the loop's supersede check compared against the value captured at loop start, saw its own rebuild as a foreign takeover, and abandoned after a single failed attempt — with the Player already torn down by the preceding cleanup, playback then stayed dead for the whole outage. The loop now adopts the generation its own attempt produced, so only genuinely foreign rebuilds and teardowns stop it. Second, the schedule was a fixed ten attempts totalling about three minutes, after which the loop exited entirely; any longer outage left nothing running to notice the network returning, and only the Swift watchdog's 120-second forced reinitialize — or a manual play — could recover it. Backoff now caps at 30 seconds and keeps retrying. This is not idle polling: the loop exists only while disconnected and exits on any lifecycle event, since every iteration re-checks the generation and the teardown flags
- Recovery is now generation-safe, closing a race where Swift and Rust could end up on different session generations. Two problems: the player event listener's stale-session check compared `EVENT_LISTENER_GENERATION` against `SESSION_GENERATION`, but the former was written to the latter's new value on every bump — so the two were always equal and the check could never reject anything. And the reconnect loop was guarded only by a `RECONNECTING` flag, which says "a loop is running", not "the thing it is fixing still exists": it could sleep up to 30 seconds between attempts, wake after a manual restart or a logout had already rebuilt or torn everything down, and rebuild over the top with a stale token. Each listener now captures its own generation (possible only because a rebuild replaces the listener along with its session — the old global existed because soft reconnect kept one listener alive across sessions), the reconnect loop abandons if its generation moved or a teardown started, checked both after each backoff sleep and after the token round-trip, and `spotifly_cleanup` invalidates the generation up front so anything in flight notices. `EVENT_LISTENER_GENERATION` is gone. Five new unit tests cover the rules
- Fixed a "Publishing changes from background threads is not allowed" runtime warning, and the thread-safety hole behind it. The Combine subjects bridging Rust callbacks into Swift are `nonisolated(unsafe)` globals reached from Rust's own threads, and only three of the eleven callbacks hopped to the main actor before sending — the other eight relied on every subscriber remembering `.receive(on: DispatchQueue.main)`. That unwritten invariant broke as soon as a SwiftUI `.onReceive` subscribed to the connection snapshot, because `.onReceive` delivers on whatever thread the publisher emits on. All non-audio callbacks now hop first, which also closes a real hazard a subscriber-side hop never could: several Rust tasks (player event listener, cluster listener, reconnect loop) can publish concurrently, and Combine subjects are not safe against concurrent `send` — `.receive(on:)` hops only *after* the subject has already delivered. Audio data keeps its separate real-time-safe path
- Initialization no longer reports success before the player is usable. `PlaybackViewModel` set `isInitialized` as soon as the FFI initializer returned, then polled `isSpircReady` for five seconds and ignored the timeout — so Swift could permanently believe the player was up while every Connect command failed, and `initializeIfNeeded` would then refuse to retry because the flag was already true. Readiness is now the authoritative condition (session connected **and** Spirc ready), a timeout is treated as failure, and the flag stays false so the next caller retries. On the Rust side, `spotifly_init_player` no longer falls back to a bare `session.connect()` when Spirc initialization fails: every Spotifly control goes through Spirc, so a connected session without one is not a player, and returning success for it was what made the unusable state permanent
- A stale Web API response can no longer overwrite newer state from Rust. `fetchInitialPlaybackState` fetched playback and queue data and applied both unconditionally when the requests completed, but Rust callbacks can arrive while those requests are in flight — so after a reconnect or transfer Swift could briefly show the correct live state and then replace it with an older network snapshot. `AppStore` now carries a monotonic `liveStateRevision` that is bumped whenever authoritative playback or queue state from Rust is accepted; the bootstrap captures it before issuing its requests and discards the response if it moved. One counter covers both playback and queue: it is coarser than tracking them separately, but the only cost is occasionally dropping bootstrap data that the live callbacks are already replacing. Provisional `SetQueue` notifications deliberately do not bump it, since they carry no usable queue and the Web API refresh they schedule must not be treated as stale. This replaces relying on the Web API `timestamp`, which was only ever used to compensate the position anchor *within* a response and was never compared against anything Rust had published
- Whether Spotifly is the active Connect device is now one derived fact instead of two competing ones. Rust tracked it in an `IS_ACTIVE_DEVICE` atomic written from fourteen scattered command and event sites and never reconciled against the cluster, while the cluster listener separately pushed the active device ID to Swift's `AppStore` — so playback routing (which read the atomic) and the views (which read the store) could disagree about whether Spotifly or a remote speaker was active, especially around external transfers. The cluster listener now computes `is_active = cluster.active_device_id == own_device_id` (the same comparison `SpircTask` makes internally) and publishes it in the connection snapshot, so both readers see the same value. Also: an empty active-device ID is no longer dropped, so "nothing is playing anywhere" clears the state instead of leaving the last active device shown forever; and `PlayerEvent::Stopped` no longer clears active-device state, which had made local playback simply ending look like a remote device taking over
- Swift no longer drives reconnection or Web API refetches from Connect activation. The two FFI callbacks are renamed to what they actually report (`spotifly_register_became_active_callback` / `..._became_inactive_callback`, surfaced as `SpotifyPlayer.becameActive` / `.becameInactive`), and `LoggedInLifecycleModifier` now keys off readiness transitions in the connection snapshot instead. Previously the activation callback triggered a full `fetchInitialPlaybackState`, so **every** device handoff fired an unguarded Web API bootstrap that could overwrite live Rust state — the most likely cause of Swift and Rust disagreeing about what was playing — while the deactivation callback armed a watchdog that would force a full reinitialize. Both now fire only on genuine connect/disconnect transitions, and the initial rise to ready is skipped because startup already bootstraps once
- The deactivation callback no longer doubles as a reconnect-failure signal. It was fired both by Spirc (meaning "another device took over", immediately) and by the reconnect loop after all ten attempts were exhausted (meaning "recovery gave up", late), so one callback carried two unrelated meanings with wildly different timing. Exhaustion is now reported only through the connection snapshot, which already carries `last_error` and the attempt count
- Handing playback off to another Spotify device no longer looks like a network outage. librespot emits `SessionDisconnected` when the local Connect device becomes **inactive**, not when the session fails — `SpircTask::handle_disconnect()` runs on an explicit disconnect, on shutdown, and on any cluster update that gives the active role to another device (this is upstream behavior, not part of the Spotifly patch). Rust treated every one of those as a dead session: it marked the connection disconnected and started a reconnect loop against a perfectly healthy session, so playing to a phone or speaker could show a disconnected UI and fire an unnecessary reconnect. The event now updates active-device state only, and recovery starts solely from real transport evidence — a `Session` that reports itself invalid, the cluster/dealer stream ending, or an explicit force-reconnect. The session-validity check preserves the one genuine failure this event does report (librespot calls `handle_disconnect` when the Spirc task shuts down unexpectedly, which the cluster listener can miss while the dealer stream is still open)
- The connection snapshot's "connected" facts now come from the point where the connection is actually established. `connected_since_ms`, the reconnect backoff counter, and `last_error` were reset in the `SessionConnected` handler, which fires on Connect *activation* and can happen repeatedly over one healthy session; they now reset where the session and Spirc are created. `SessionConnected` only records the connection id and marks the device active
- Player initialization and restart are now serialized through one stored `Task`. `forceReinitialize` and `initializeIfNeeded` both ran `SpotifyPlayer.initialize`, which performs a Rust cleanup followed by a rebuild — and `@MainActor` prevents them running simultaneously but not overlapping, since every `await` is a suspension point another caller can enter. Two overlapping calls could interleave one call's cleanup with the other's rebuild, leaving Swift holding state for a Rust generation that had already been replaced. Late callers now await the in-flight run instead of starting a competing one, which also coalesces the genuinely concurrent triggers: system wake and the reconnect watchdog can fire together, and one rebuild is the correct response to both. The two near-duplicate bodies collapsed into one, and `isInitialized` is cleared up front so a restart whose `initialize()` throws no longer leaves the flag stuck true
- Playback commands no longer report success for actions Rust rejected. Three paths bypassed the connectivity guards that `next`/`previous`/`pause`/`resume`/`toggleShuffle` already had: `togglePlayPause` called the unguarded `SpotifyPlayer.pause()` FFI wrapper directly and asserted `isPlaying = false` itself (instead of routing through the view model's guarded `pause()`, which also carries the Web API fallback for remote devices and leaves the flag to the Mercury callback); `stop()` cleared track and playing state even when the session was down; and `performSeek` had no guard at all, so during a short outage the progress bar stayed parked at a position playback never reached. `performSeek` now re-syncs the anchor from the real position when the command can't be sent, which keeps scrubbing feedback immediate without lying about the result
- Transferring playback to another device no longer reports success unconditionally. `DeviceService.transferPlayback` optimistically marked the target active and returned `true` while the FFI call ran detached and its `SpotiflyResult` was discarded, so a rejected transfer (no session, invalid session, SpClient failure) left the device list showing a device that never became active. The two transfer wrappers now return whether Rust accepted the command, and a rejected transfer rolls the optimistic update back to the previous active device and returns `false`
- Opening a playlist no longer fails for newer/stricter Spotify developer accounts. `fetchPlaylistTracks` was still calling the deprecated `GET /playlists/{id}/tracks` endpoint, which Spotify now rejects with `403` for apps approved after the API tightened — `fetchPlaylistDetails()` would succeed but the tracks fetch failed, so the whole playlist appeared broken even though the playlist list loaded fine. Switched to `GET /playlists/{id}/items` (the documented replacement) and added pagination via the response's `next` URL, since the new endpoint caps at 50 items per page versus the old endpoint's 100
- Opening a playlist for the first time no longer occasionally fails with a cancellation error. `PlaylistDetailView` lives in the list+detail split that appears when Playlists switches from 2 to 3 columns, so the detail view could be recreated mid-fetch, re-triggering its `.task` and firing a second, untracked `fetchPlaylistDetails` request; when the original view was torn down its in-flight request was cancelled and the surviving view surfaced that as an error. `PlaylistService.fetchPlaylistDetails` now dedups in-flight requests per playlist ID via a stored `Task` (matching the pattern used by `AlbumService`/`ArtistService`/`PlaylistService`'s own user-playlists load), so a re-triggered `.task` awaits the existing request instead of racing a new one
- Playlist, album, and artist rows in the sidebar lists are now clickable across their full width instead of only over the cover art and label. The rows were full-width `Button`s with `.buttonStyle(.plain)`, but on macOS that style's hit-testing doesn't reliably honor `.contentShape(Rectangle())` over a transparent `Spacer()` region — clicks only registered over the actual rendered image/text content even though the row's layout and selection highlight already spanned the full width. Replaced the `Button` wrapper with a plain `HStack` plus `.onTapGesture(perform:)`, which does respect `contentShape` consistently
- Restored the always-visible search field in the top toolbar. A previous refactor had switched it to the `.searchable(text:isPresented:)` variant, which hides the field unless `isPresented` is true (and it defaulted to false), so the field had disappeared. It is again attached to the `NavigationSplitView` as a plain `.searchable(text:)`, visible in every section
- Reworked the logged-in window layout to an Apple Music-style hierarchy: a single, stable two-column `NavigationSplitView` (sidebar | content region). The 2- vs 3-column variation now happens *inside* the content region (a single section view, or a list + detail `HSplitView`), so the sidebar column is never recreated — its width stays put across every section switch and no longer snaps between per-layout defaults. The now-playing bar is overlaid on the content region, so it centers over column 2 (or columns 2+3) without the previous sidebar-width math
- Volume changes during local playback now take effect immediately instead of lagging by up to ~2 seconds. Volume was applied by librespot's software mixer in Rust, baking the gain into PCM that then sat in the render buffer, so changes were only heard once that buffer drained. The Rust player now uses `NoOpVolume` (no sample attenuation) and gain is applied at the output via `AVSampleBufferAudioRenderer.volume`, which scales audio as it plays. The slider value is passed through librespot's default logarithmic taper (`VolumeCtrl::Log`, 60 dB) so the perceived curve is unchanged, and the soft mixer still tracks the logical volume so Spotify Connect reporting and remote volume control are unaffected
- Favorites no longer intermittently render the empty "No favorites yet" state despite the `/me/tracks` request firing. The load was tied to the Favorites view's `.task`, so when the view was recreated (navigation/column-layout change) mid-request the in-flight load was cancelled, and a recreated view's `.task` could observe `isLoading == true` and bail — leaving the list stuck empty until a manual refresh. `TrackService.loadFavorites` now uses the stored-unstructured-`Task` dedup pattern (matching `AlbumService`/`ArtistService`) so the load survives caller cancellation, and `TrackService` is persisted via `@State` in `LoggedInView` so the in-flight task reference survives view recreation
- Handle Spotify's upcoming refresh-token expiration (refresh tokens expire after six months starting July 20, 2026): `invalid_grant` responses are now detected as a distinct `SpotifyAuthError.tokenRevoked`, the stored token is discarded instead of retried, and an expired/revoked token mid-session now invalidates `SpotifySession` and routes the user back to the sign-in flow rather than silently looping on a dead access token
- Starting song radio from the currently playing track now seeks with the same interpolated playback position the UI uses, avoiding stale-position jumps when the radio context loads
- Fixed the Now Playing overlay (menu bar) not updating when a song auto-advances during album/playlist playback
- Favorites now resolve via batched `/me/tracks/contains` checks for the tracks actually shown in album, playlist, queue, search, and now-playing views instead of depending on a full favorites preload
- Saving and removing favorite tracks now uses Spotify's saved-tracks endpoint correctly, so heart toggles persist again across Spotify clients
- Clicking Favorites in the sidebar now loads the favorites list automatically again, and the first real favorites fetch replaces any optimistic placeholder entries instead of appending to them
- Navigation history is now tracked consistently across sidebar section switches, library detail selections, and pushed search destinations, with shared back/forward controls in the content toolbar
- Back/forward history restores no longer depend on a next-runloop reset flag; history recording is now suppressed until the exact restored snapshot is reached
- Search-result drill-down navigation now stores track IDs instead of full track payloads, so back/forward history does not retain large copies of search result arrays
- The navigation coordinator API no longer exposes ignored section/selection context parameters, and card/caller plumbing for those dead arguments has been removed
- Navigation history cleanup: removed the trivial back wrapper and documented why section switches clear the visible stack before history snapshots are recorded
